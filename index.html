1. Java 基础

1.1 谈谈 Java 的跨平台原理

Java 源码编译为字节码（.class），由 JVM 解释/编译执行。不同操作系统安装对应 JVM，字节码无需重新编译即可运行，实现「一次编写，到处运行（Write Once, Run Anywhere）」。

1.2 JDK、JRE、JVM 的关系

  • JVM：Java 虚拟机，负责执行字节码。
  • JRE：Java 运行时环境，包含 JVM + 核心类库，用于运行程序。
  • JDK：Java 开发工具包，包含 JRE + 编译器（javac）、调试工具等，用于开发。
  • 关系：JDK ⊃ JRE ⊃ JVM。

1.4 == 与 equals 的区别

  • ==：比较基本类型的值；比较引用类型的地址。
  • equals：Object 默认等价于 ==，但多数类（如 String、Integer）重写了它来比较内容。
  • 重写 equals 必须重写 hashCode（否则 HashMap 等行为异常）。

1.5 String、StringBuffer、StringBuilder

  • String：不可变（final char[]），每次拼接产生新对象，线程安全。
  • StringBuffer：可变，方法加 synchronized，线程安全，效率低。
  • StringBuilder：可变，非线程安全，效率高（单线程首选）。
  • 字符串拼接建议：少量用 +（编译优化为 StringBuilder）；循环内必须用 StringBuilder。

1.6 String 为什么不可变？好处是什么？

  • 底层 private final char[]（Java 9 后为 byte[] + coder），final 保证引用不变，private 且无修改方法。
  • 好处：字符串常量池可复用、线程安全、适合做 HashMap 的 key、类加载安全。

1.7 重写（Override）与重载（Overload）

  • 重载：同一类中，方法名相同、参数列表不同（类型/个数/顺序），与返回值无关。编译期多态。
  • 重写：子类重写父类方法，方法签名相同，访问修饰符不能更严格，抛出的异常不能更宽泛。运行期多态。

  • final：修饰类不可继承、方法不可重写、变量不可变（引用不可变，对象内容可变）。

  • finalize：Object 的方法，GC 前调用，已废弃（Java 9+ 标记 deprecated），不要用。

1.10 什么是反射？优缺点？

  • 运行时获取类信息并操作对象（Class、Method、Field）。框架（Spring、MyBatis）大量使用。
  • 优点：解耦、动态加载、提高灵活性。
  • 缺点：破坏封装、性能略低、安全受限。

2. 面向对象

2.1 三大特性

  • 封装：隐藏实现细节，暴露接口，提高安全性与可维护性。
  • 继承：子类复用父类代码，单继承（类）/ 多实现（接口）。
  • 多态：同一接口不同实现，父类引用指向子类对象，运行期绑定。

2.2 面向对象 vs 面向过程

  • 面向过程：以函数/步骤为中心，性能略高，适合简单场景。
  • 面向对象：以对象为中心，易扩展、易维护，适合大型系统。

3.2 ArrayList vs LinkedList

  • ArrayList：基于动态数组，随机访问 O(1)，插入删除（非尾部）需移动元素 O(n)，扩容 1.5 倍。
  • LinkedList：基于双向链表，插入删除 O(1)（已知节点），随机访问 O(n)，额外内存开销（前后指针）。

3.3 HashMap 原理（重点）

  • JDK 1.7：数组 + 链表，头插法（多线程易成环）。
  • JDK 1.8：数组 + 链表 + 红黑树。
  • 默认容量 16，负载因子 0.75，阈值 = 容量 × 负载因子。
  • 链表长度 ≥ 8 且数组容量 ≥ 64 时转红黑树；树节点 ≤ 6 退化为链表。
  • 计算下标：(n - 1) & hash，hash 经 hashCode ^ (h >>> 16) 扰动。
  • 扩容 2 倍，重新分布（低位/高位链表）。
  • 线程不安全：并发 put 可能导致数据覆盖、死循环（1.7）。并发场景用 ConcurrentHashMap。

3.4 ConcurrentHashMap

  • JDK 1.7：Segment 分段锁（ReentrantLock），默认 16 段。
  • JDK 1.8：取消 Segment，使用 Node + CAS + synchronized（锁链表头节点），粒度更细，效率更高。

3.5 HashSet 如何保证不重复

  • 基于 HashMap 实现，元素作为 key，value 为固定 Object。靠 hashCode() + equals() 判断重复。

3.6 fail-fast 与 fail-safe

  • fail-fast：遍历时若集合被修改（非迭代器自身），抛出 ConcurrentModificationException。ArrayList 等默认。
  • fail-safe：基于副本遍历，不抛异常，但读到的是旧数据。CopyOnWriteArrayList、ConcurrentHashMap 迭代器。

4. 并发与多线程（JUC）

4.1 进程与线程

  • 进程：资源分配的最小单位，独立内存空间。
  • 线程：CPU 调度的最小单位，同进程内线程共享内存。

4.2 创建线程的方式

  1. 继承 Thread 重写 run。
  2. 实现 Runnable（无返回值）。
  3. 实现 Callable（有返回值，配合 FutureTask）。
  4. 线程池 ExecutorService。

4.3 线程的生命周期

新建 → 就绪 → 运行 → 阻塞（wait/sleep/IO/锁）→ 死亡。

  • sleep：不释放锁，Thread 静态方法。
  • wait：释放锁，Object 方法，需配合 notify/notifyAll，在 synchronized 内调用。

4.4 synchronized 关键字

  • 修饰方法/代码块，保证原子性、可见性、有序性。
  • 底层：对象头 Mark Word + Monitor（管程）。JDK 1.6 后引入锁升级：无锁 → 偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁（操作系统互斥）。

4.5 volatile

  • 保证可见性（写立即刷主存，读从主存取）与有序性（禁止指令重排）。
  • 不保证原子性（如 i++ 仍是三步操作）。
  • 经典用法：状态标志位、双重检查单例。

4.7 锁分类

  • 公平/非公平锁：是否按申请顺序获取（ReentrantLock 可设置，默认非公平）。
  • 可重入锁：同一线程可重复获取（synchronized、ReentrantLock）。
  • 悲观锁/乐观锁：synchronized 是悲观；CAS 是乐观。
  • 自旋锁：失败后忙等一段时间，避免线程切换开销。
  • 读写锁：ReadWriteLock，读共享、写独占。

4.8 CAS 是什么？有什么问题？

  • Compare And Swap：比较并交换，无锁原子操作（CPU 指令级）。
  • 问题：ABA 问题（加版本号/时间戳解决，如 AtomicStampedReference）、自旋开销大、只能保证一个变量原子性。

4.9 线程池

  • 核心参数（ThreadPoolExecutor）：
  • corePoolSize：核心线程数
  • maximumPoolSize：最大线程数
  • keepAliveTime：空闲线程存活时间
  • workQueue：任务队列（ArrayBlockingQueue、LinkedBlockingQueue、SynchronousQueue）
  • threadFactory：线程工厂
  • handler：拒绝策略
  • 执行流程：核心线程满 → 入队列 → 队列满 → 开非核心线程 → 达最大线程数 → 触发拒绝策略。
  • 拒绝策略：AbortPolicy（抛异常，默认）、CallerRunsPolicy（调用者线程执行）、DiscardPolicy（丢弃）、DiscardOldestPolicy（丢弃最老）。
  • Executors 的隐患：FixedThreadPool / SingleThreadPool 用无界队列易 OOM；CachedThreadPool 最大线程数无界易 OOM。建议手动 new ThreadPoolExecutor。

4.10 ThreadLocal

  • 线程本地变量，每个线程有独立副本，避免共享。
  • 原理：Thread 内有 ThreadLocalMap，key 为 ThreadLocal 弱引用。
  • 内存泄漏：key 弱引用被 GC 后 value 仍是强引用，需手动 remove()。

5. JVM

5.1 运行时数据区

  • 线程私有：程序计数器、虚拟机栈、本地方法栈。
  • 线程共享：堆、方法区（元空间 Metaspace，JDK 8 取代永久代）。

5.2 堆内存划分

  • 新生代（Eden + 两个 Survivor S0/S1）、老年代。
  • 对象优先在 Eden 分配，Minor GC 后存活的进入 Survivor，年龄达阈值（默认 15）进入老年代。

5.3 垃圾回收算法

  • 标记-清除：简单但有碎片。
  • 标记-整理：无碎片，移动对象开销大（老年代）。
  • 复制算法：无碎片，浪费一半空间（新生代）。
  • 分代收集：新生代用复制，老年代用标记-整理/清除。

5.4 垃圾收集器

  • Serial / Serial Old：单线程，简单。
  • ParNew：Serial 多线程版，配合 CMS。
  • Parallel Scavenge / Parallel Old：吞吐量优先。
  • CMS：并发标记清除，低停顿，但碎片、CPU 敏感、Concurrent Mode Failure。
  • G1：分 Region，可预测停顿，兼顾吞吐与延迟（JDK 9+ 默认）。
  • ZGC / Shenandoah：超低停顿（毫秒级）。

5.5 如何判断对象可回收？

  • 引用计数：简单但有循环引用问题。
  • 可达性分析：GC Roots（栈引用、静态变量、常量、JNI）不可达即为可回收。至少两次标记（finalize 自救一次）。

5.6 双亲委派模型

  • 类加载器层级：Bootstrap → Extension → Application → 自定义。
  • 加载时先委派父加载器，父无法加载才自己加载。
  • 好处：避免重复加载、防止核心类被篡改。
  • 破坏场景：SPI（JDBC）、热部署、Tomcat WebAppClassLoader。

5.7 常见 OOM / 调优参数

  • -Xms / -Xmx：堆初始/最大。
  • -Xmn：新生代大小。
  • -XX:MetaspaceSize：元空间。
  • 排查工具：jps、jstat、jmap、jstack、jvisualvm、Arthas。

7. I/O 与 NIO

7.1 BIO / NIO / AIO

  • BIO：同步阻塞，一连接一线程。
  • NIO：同步非阻塞，基于 Channel + Buffer + Selector（多路复用），一个线程管多个连接。
  • AIO：异步非阻塞（NIO.2），回调通知。

7.2 NIO 核心组件

  • Channel：双向通道（读写）。
  • Buffer：数据容器（position、limit、capacity）。
  • Selector：多路复用器，监听多个 Channel 事件。

1. 集合：购物车与商品去重

业务背景 用户加购同一商品多次，前端可能重复提交；购物车需要展示「不重复的商品 + 各自数量」。

用到的知识点

  • HashMap：以 skuId 为 key，数量 为 value，天然去重。
  • LinkedHashMap：需要保持加购顺序时选用。
  • HashSet：批量校验「已存在的 skuId 集合」。
  • 不可变对象做 key 时必须正确重写 equals + hashCode（SKU 用 id 即可）。

关键实现思路

Code
Map<Long, Integer> cart = new LinkedHashMap<>();
for (SkuItem item : items) {
    cart.merge(item.getSkuId(), item.getCount(), Integer::sum); // 合并数量
}

面试追问

  • 为什么购物车不用 List 而用 Map？（O(1) 查重 vs O(n)）
  • 如果 skuId 是对象，hashCode 冲突会怎样？（退化成链表/红黑树，性能下降）
  • 并发加购怎么办？（用 ConcurrentHashMap，或用数据库唯一约束兜底）

2. HashMap / ConcurrentHashMap：本地缓存与热点计数

业务背景 商品详情页高频访问，DB 扛不住，加一层本地缓存；同时实时统计「商品被浏览次数」做热门榜单。

用到的知识点

  • ConcurrentHashMap 做本地缓存（Caffeine 底层也是它 + 近似 LRU）。
  • 并发计数用 ConcurrentHashMap + LongAdder（分段 CAS，比 AtomicLong 高并发更优）。
  • 缓存与 Redis 的层级关系（本地缓存 → Redis → DB）。

关键实现思路

Code
private final Map<Long, ProductVO> cache = new ConcurrentHashMap<>();
private final Map<Long, LongAdder> viewCount = new ConcurrentHashMap<>();

public ProductVO getProduct(Long id) {
    return cache.computeIfAbsent(id, this::loadFromDb);
}
public void incrView(Long id) {
    viewCount.computeIfAbsent(id, k -> new LongAdder()).increment();
}

面试追问

  • 本地缓存和 Redis 缓存各自优缺点？（本地最快但各节点不一致，Redis 集中但有网络开销）
  • 为什么热点计数用 LongAdder 而不是 AtomicLong？（高并发下 AtomicLong CAS 竞争激烈，LongAdder 分 cell 分散竞争）
  • 缓存一致性怎么保证？（更新 DB 后删本地缓存 + 发广播/消息让其他节点失效）

3. synchronized / 锁：秒杀库存扣减

业务背景 秒杀活动，1 万人在同一秒抢 100 件商品，必须保证「不超卖、不超扣」。

用到的知识点

  • 单机：synchronized / ReentrantLock 保护库存扣减临界区。
  • 分布式：必须上分布式锁（Redis SETNX / Redisson）或数据库乐观锁（UPDATE ... WHERE stock > 0）。
  • CAS / 原子类在单体场景的替代。

关键实现思路（单体 + 数据库乐观锁兜底）

Code
// 先 Redis 预扣（Lua 原子脚本保证原子性）
Long remain = redisTemplate.execute(decrScript, List.of(stockKey));
if (remain < 0) { redisTemplate.incr(stockKey); return "售罄"; }
// 异步落库，数据库再 WHERE stock>0 兜底防超卖
int rows = itemMapper.decrStock(itemId);
if (rows == 0) { redisTemplate.incr(stockKey); return "售罄"; }

面试追问

  • 只靠 synchronized 为什么扛不住秒杀？（单机锁，集群多实例各自扣自己的，照样超卖）
  • 为什么用 Lua 脚本做 Redis 预扣？（保证「判断+扣减」原子，避免 check-then-act 竞态）
  • 库存扣成负数怎么防？（Lua 返回后判断 + 数据库 WHERE 条件双重保险）

4. volatile：系统开关与单例配置中心

业务背景

  • 运营要临时关闭某个营销活动（如「双11预热」），不想发版就能即时生效。
  • 配置中心（如 Nacos/Apollo）推送配置后，应用要立刻读到新值。

用到的知识点

  • volatile 保证可见性：一个线程改了，其他线程立刻可见。
  • 典型用法：布尔开关 private volatile boolean activityOn;。
  • 不能保证原子性：开关只是赋值 OK，但 i++ 类的计数不行。

关键实现思路

Code
@Component
public class ActivitySwitch {
    private volatile boolean open = false;
    @Value("${activity.open:false}") public void setOpen(boolean v){ this.open = v; }
    public boolean isOpen(){ return open; }
}

面试追问

  • 为什么开关用 volatile 而不是 synchronized？（开关只是写读布尔值，volatile 无锁更轻量）
  • 配置中心推送后为什么能立刻生效？（监听器 set 新值 + volatile 保证可见）
  • 单例 DCL 为什么必须 volatile？（防止指令重排导致返回半初始化对象）

5. 线程池：异步通知与批量任务

业务背景 用户下单成功后，要发短信、推 App、记积分、写流水——这些不能阻塞下单主流程，且是大批量任务。

用到的知识点

  • 自定义 ThreadPoolExecutor，不用 Executors（防 OOM）。
  • 核心/最大线程数、队列、拒绝策略选型。
  • CompletableFuture 编排多个异步任务。

关键实现思路

Code
ExecutorService notifyPool = new ThreadPoolExecutor(
    8, 32, 60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1024),
    new ThreadFactoryBuilder().setNameFormat("notify-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()); // 拒绝时由调用方线程执行，不丢任务

CompletableFuture.runAsync(() -> smsService.send(order), notifyPool)
    .thenRunAsync(() -> pointService.add(order), notifyPool);

面试追问

  • 为什么不用 newCachedThreadPool？（最大线程数无界，瞬时洪峰直接 OOM）
  • 拒绝策略为什么选 CallerRunsPolicy？（不下单主链路、不丢通知，压力回灌调用方限流）
  • 任务执行异常怎么感知？（重写 afterExecute 或 Future.get 捕获）

6. ThreadLocal：用户上下文与链路追踪

业务背景 一次请求里多处需要「当前登录用户」「TraceId」，不想每层方法都传参；同时要避免用户信息串号。

用到的知识点

  • ThreadLocal 存请求级上下文（UserContext、MDC TraceId）。
  • 必须 remove()，否则线程池复用导致串数据（内存泄漏 + 串号）。
  • Spring MVC 拦截器 preHandle 设值、afterCompletion 清理。

关键实现思路

Code
public class UserContext {
    private static final ThreadLocal<User> TL = new ThreadLocal<>();
    public static void set(User u){ TL.set(u); }
    public static User get(){ return TL.get(); }
    public static void clear(){ TL.remove(); } // 关键！
}

面试追问

  • 为什么线程池里不 remove 会串号？（线程复用，下次请求读到上次的 user）
  • ThreadLocal 内存泄漏原因？（key 弱引用被 GC，value 强引用残留，remove 清理）
  • TraceId 怎么跨线程传递？（InheritableThreadLocal 或 TransmittableThreadLocal 解决线程池透传）

7. JVM / GC：大促接口超时排查

业务背景 大促期间，订单接口每隔几分钟就出现一波 1~2 秒超时，平时正常。

用到的知识点

  • GC 日志分析（-Xlog:gc* / -XX:+PrintGCDetails）。
  • 频繁 Full GC 导致 Stop-The-World，请求被「冻结」。
  • 排查链路：监控告警 → 看 GC 频次/耗时 → 堆 dump 分析大对象 → 定位内存泄漏/缓存无上限。

关键实现思路

Code
# 抓现场
jstat -gcutil <pid> 1000      # 看各区占用与 GC 次数
jmap -dump:live,format=b,file=heap.hprof <pid>  # 堆转储
# 用 MAT / VisualVM / Arthas 分析：谁占了多少
  • 常见根因：本地缓存 HashMap 无上限、ThreadLocal 未 remove、大对象（一次性读全表）。

面试追问

  • Full GC 和 Young GC 区别？（回收范围、触发条件、停顿时长）
  • 为什么大促才出问题平时没事？（流量翻倍触发缓存膨胀 / 对象分配速率陡增）
  • 怎么预防？（缓存加容量上限+过期、压测、监控 GC 告警）

8. String：订单号与金额拼接

业务背景 生成订单号、拼接用户地址、格式化金额展示——字符串处理到处都是。

用到的知识点

  • 循环内拼接用 StringBuilder（不用 +，避免产生大量临时对象）。
  • 金额绝不用 double（精度丢失），用 BigDecimal + String 构造。
  • String.format / DecimalFormat 做展示。

StringBuilder sb = new StringBuilder();

9. 设计模式：支付与促销策略

业务背景

10. MySQL 索引：订单查询慢 SQL

业务背景 运营后台「查某用户最近 3 个月订单」，未加索引时全表扫描，接口 5 秒。

用到的知识点

  • 联合索引 (user_id, create_time) 命中最左前缀，既能按用户又能按时间范围。
  • 避免索引失效：不要在字段上套函数（WHERE DATE(create_time)=... 会失效）、避免 %前缀 模糊。
  • 覆盖索引避免回表（SELECT 只取索引列）。

关键实现思路

Code
-- 建联合索引
ALTER TABLE orders ADD INDEX idx_user_time (user_id, create_time);
-- 查询（走索引，范围在右列）
SELECT id, amount FROM orders
WHERE user_id = 123 AND create_time >= '2026-05-01'
ORDER BY create_time DESC LIMIT 20;

面试追问

  • 为什么联合索引顺序是 user_id 在前？（高频等值查询在前，范围在后，否则索引失效）
  • 怎么验证走没走索引？（EXPLAIN 看 type/key/rows/extra）
  • 回表是什么？（二级索引存主键，需再用主键查整行；覆盖索引可免）

11. 事务：下单扣库存与转账

业务背景 下单要「扣库存 + 创建订单 + 扣余额」要么全成功要么全失败；银行转账 A 减 B 加必须原子。

用到的知识点

  • @Transactional 声明式事务（AOP 代理）。
  • 事务隔离级别解决脏读/不可重复读/幻读。
  • 事务失效场景：同类自调用、非 public、异常被吞。
  • 跨服务用分布式事务（Seata TCC / 消息最终一致性）。

关键实现思路

Code
@Transactional(rollbackFor = Exception.class, isolation = Isolation.REPEATABLE_READ)
public void createOrder(OrderCmd cmd){
    stockMapper.decr(cmd.getSkuId(), cmd.getCount()); // 扣库存
    orderMapper.insert(cmd.toOrder());                // 建订单
    accountMapper.decr(cmd.getUserId(), cmd.getAmount()); // 扣款
    // 任一异常整体回滚
}

面试追问

  • 为什么自调用事务不生效？（Spring 走代理，内部调用没过代理，没织入事务）
  • 扣库存和扣款不在同一个库怎么办？（跨库 → 分布式事务 / 最终一致 + 补偿）
  • 大事务有什么危害？（锁久、连接占用、回滚慢，应拆解 + 异步）

12. Redis：缓存与分布式锁

业务背景

  • 商品详情缓存，扛读流量。
  • 秒杀 / 定时任务防止集群多节点重复执行。

用到的知识点

  • 缓存三大坑：穿透（布隆过滤器）、击穿（互斥锁/逻辑过期）、雪崩（过期时间加随机）。
  • 分布式锁：SET key value NX EX 原子加锁 + Lua 释放（防误删）+ Redisson 看门狗自动续期。
  • 缓存与 DB 一致性：先更新 DB 再删缓存（Cache-Aside）。

关键实现思路

Code
// 加锁（Redisson 简化写法）
RLock lock = redissonClient.getLock("task:sync");
if (lock.tryLock(0, 30, TimeUnit.SECONDS)) {
    try { doSync(); } finally { lock.unlock(); }
}
// 缓存读取
Product p = redis.get(key);
if (p == null) {
    p = db.load(id);
    redis.setex(key, 300 + RandomUtil.randomInt(60), p); // 过期加随机防雪崩
}

面试追问

  • 为什么释放锁要用 Lua？（判断+删除必须原子，否则可能删掉别人的锁）
  • 缓存和数据库不一致怎么解决？（更新 DB 后删缓存；延迟双删兜底）
  • Redisson 看门狗做什么？（锁快过期时自动续期，防止业务没跑完锁没了）

13. Spring：循环依赖 / AOP / 事务失效

业务背景

  • 支付服务 A 依赖风控服务 B，B 又依赖 A（循环依赖）。
  • 统一记录接口耗时、统一登录校验。

用到的知识点

  • 循环依赖：Spring 用三级缓存解决（singletonObjects / earlySingletonObjects / singletonFactories），允许「提前暴露半成品 bean」注入。
  • AOP：用动态代理织入日志、鉴权、事务（JDK 代理基于接口，CGLIB 基于继承）。
  • 事务失效：自调用、异常被 catch、非 public、数据库引擎不支持。

关键实现思路

Code
@Aspect @Component
public class LogAspect {
    @Around("execution(* com.x..service..*(..))")
    public Object log(ProceedingJoinPoint pjp) throws Throwable {
        long s = System.currentTimeMillis();
        try { return pjp.proceed(); }
        finally { log.info("{} 耗时{}ms", pjp.getSignature(), System.currentTimeMillis()-s); }
    }
}

面试追问

  • 三级缓存具体怎么破循环依赖？（一二三级分别存成品/早期引用/工厂，提前曝光解决）
  • 构造器注入的循环依赖能解决吗？（不能，需 @Lazy 或改设计）
  • 为什么 CGLIB 能代理类而 JDK 只能代理接口？（CGLIB 生成子类，JDK 用 InvocationHandler）

14. 网络：接口超时与 HTTPS

业务背景

15. 消息队列：下单异步解耦

业务背景 下单成功后要做 5 件周边事（发券、积分、通知、风控、对账）。若同步做，任一失败则下单失败，且慢。

1.3 网关（Gateway）作用

  • 路由：根据断言（Path、Header、Cookie）转发到对应服务。
  • 鉴权：统一 JWT / OAuth2 校验，拦截非法请求。
  • 限流：基于令牌桶 / 计数器，保护后端。
  • 灰度 / 熔断：按版本路由、集成 Sentinel 熔断。

1.4 负载均衡：Ribbon vs Nginx

  • Ribbon：客户端负载均衡（进程内，知道所有实例，选一个再调）。
  • Nginx：服务端负载均衡（独立节点，集中转发）。
  • 区别：Ribbon 减少一跳、支持更细策略；Nginx 与语言无关、可做 L4/L7。

1.5 熔断、降级、限流

  • 熔断：错误率/慢调用超阈值，打开熔断器，一段时间后半开探测（Sentinel 三种状态）。
  • 降级：流量激增或依赖故障时，返回兜底（默认值 / 缓存 / 静态页）。
  • 限流算法：
  • 计数器（固定窗口，有临界突刺问题）。
  • 滑动窗口（细分时间片，更平滑）。
  • 漏桶（恒定速率流出，整形）。
  • 令牌桶（恒定速率发令牌，允许突发，最常用）。

面试追问

  • Eureka 与 Nacos 在 CAP 上的取舍？（Eureka 选 AP 保证可用；Nacos 可切 CP 保证强一致）
  • Sentinel 和 Hystrix 区别？（Hystrix 线程池隔离资源占用大；Sentinel 信号量 + 滑动窗口，更轻量）
  • 网关为什么要做限流而不是只靠服务自身？（边缘拦截，避免无效流量打到内网）

2. 消息队列（MQ）

2.1 为什么用 MQ

  • 解耦：生产者不关心谁消费（如下单后发券、积分、通知各自订阅）。
  • 异步：非核心链路异步化，主流程快返回。
  • 削峰：突发流量先入队，消费者按能力平稳处理（如秒杀）。

2.2 Kafka / RabbitMQ / RocketMQ 对比

2.3 消息可靠性（不丢）

  • 生产端：confirm 机制（RabbitMQ）、acks=all + 重试（Kafka）。
  • 服务端：刷盘（同步/异步）+ 主从复制。
  • 消费端：先处理业务再手动 ack，处理失败不 ack（重回队列 / 死信）。

2.4 重复消费与幂等

  • 原因：网络重试、rebalance、消费超时。
  • 幂等方案：业务唯一键（订单号）去重表、Redis SETNX、状态机（已处理则跳过）、数据库唯一索引。

2.5 消息积压处理

  • 临时扩容消费者实例 + 提升消费并发。
  • 如果消费慢：开启多线程消费 / 批量消费。
  • 极端：新建临时 Topic，把积压消息转发后快速消费。

2.6 顺序消息

  • Kafka：同一业务 key 发到同一 partition，单 partition 内有序。
  • RocketMQ：同一 MessageQueue 有序，用顺序发送 + 加锁消费。

面试追问

  • 如何保证消息不丢失？（三端确认：生产 confirm + 服务端持久化 + 消费手动 ack）
  • RocketMQ 事务消息原理？（Half Message → 执行本地事务 → Commit/Rollback，回查保证最终一致）
  • Kafka 为什么快？（顺序写磁盘、零拷贝 sendfile、批量压缩、页缓存）

3. 分布式事务

3.1 2PC / 3PC

  • 2PC（两阶段提交）：准备阶段（各参与者锁资源投票）+ 提交阶段（协调者统一提交/回滚）。缺点：同步阻塞、单点、数据不一致（协调者宕机）。
  • 3PC：引入超时与预询问，降低阻塞，但网络分区仍可能不一致，工业界少用。

3.2 TCC（Try-Confirm-Cancel）

  • Try：预留资源（如冻结库存）。
  • Confirm：真正提交（幂等）。
  • Cancel：释放预留（幂等）。
  • 优点：无长事务锁，性能好；缺点：业务侵入强，需手写三阶段。

3.3 消息最终一致性（常用）

  • 本地消息表：业务与消息同库事务，后台任务投递到 MQ，消费者幂等处理。
  • 事务消息（RocketMQ）：Half Message + 本地事务 + 回查，保证「本地成功必发消息」。
  • 特点：最终一致、性能好、容忍短暂不一致。

3.4 Seata

  • AT 模式：自动生成回滚日志（undo_log），两阶段：一阶段提交本地事务+写undo，二阶段异步清理或回滚（无侵入，最常用）。
  • TCC / SAGA / XA 模式按需选择。

3.5 最大努力通知

  • 多次重试通知 + 对账，适用于跨系统（如支付结果通知），不保证强一致，但尽力送达。

面试追问

  • 你们项目用哪种分布式事务？为什么？（电商常用 消息最终一致 / Seata AT，避免 2PC 长锁）
  • TCC 的空回滚 / 防悬挂是什么？（Try 未收到但收到 Cancel → 记录空回滚；防悬挂：Cancel 先于 Try 到达要拒绝）
  • Seata AT 为什么无侵入？（代理数据源，自动解析 SQL 生成前后镜像）

4. 分布式锁与缓存一致性

4.1 分布式锁方案

  • Redis 实现：SET key value NX EX 原子加锁；Lua 脚本释放（防误删）；Redisson 看门狗自动续期。
  • 优点：高性能；缺点：主从切换可能丢锁（RedLock 争议大）。
  • ZooKeeper 实现：临时有序节点 + 最小节点获锁 + watch 下一节点。
  • 优点：强一致、锁一定不丢；缺点：性能较低、依赖 ZK 集群。
  • 数据库实现：唯一索引 / SELECT ... FOR UPDATE。
  • 优点：简单；缺点：性能差、连接占用。

4.2 缓存与 DB 一致性

  • Cache-Aside（旁路）：读时回填，写时「先更新 DB 再删缓存」。
  • 延迟双删：更新 DB → 删缓存 → 延迟再删一次（防更新期间旧值回填）。
  • binlog 订阅（Canal）：监听 binlog 异步删/更新缓存，解耦业务。
  • 取舍：强一致几乎不可能，追求「最终一致 + 缩短不一致窗口」。

面试追问

  • Redis 锁和 ZK 锁怎么选？（高并发选 Redis；强一致选 ZK）
  • 为什么「先更新 DB 再删缓存」仍可能不一致？（删缓存后、DB 提交前读请求回填旧值 → 延迟双删/订阅 binlog 兜底）
  • Redisson 看门狗原理？（加锁后定时续期，业务完成才释放，防止锁提前过期）

5. 分布式 ID 与分库分表

5.1 分布式 ID 方案

  • UUID：简单无序，作为 DB 主键导致索引碎片化，不推荐。
  • 雪花算法（Snowflake）：时间戳+机器ID+序列号，趋势递增、高性能；依赖时钟（时钟回拨问题）。
  • 号段模式（Leaf-segment）：DB 批量取号段，内存发号，性能好。
  • Leaf-snowflake：解决时钟回拨的雪花改进。
  • 要求：全局唯一、趋势递增（利 B+ 树）、高可用、高性能。

5.2 分库分表

  • 垂直分库：按业务（订单库、用户库）拆分，解耦。
  • 水平分表：单表数据过大，按 分片键（用户ID、订单ID）哈希/范围/时间分片。
  • 中间件：ShardingSphere（JDBC 层 / Proxy）。
  • 带来的问题：
  • 分布式事务（跨库）。
  • 跨分片查询 / 分页 / 排序困难（需归并）。
  • 分片键选择不慎导致数据倾斜。
  • 扩容需迁移数据（一致性哈希可缓解）。

面试追问

1. JDK 17 / 21 新特性（T0 必考）

1.1 虚拟线程（Virtual Threads，Project Loom）★

  • 是什么：JDK 21 正式发布的轻量级线程，由 JVM 调度而非操作系统，运行在少量「载体线程（Carrier Thread）」之上。
  • 为什么需要：平台线程栈约 1–2MB，1 万并发连接就要 10–20GB 内存；虚拟线程栈仅约 1KB，可轻松创建百万级。
  • 核心原理：虚拟线程阻塞在 I/O 上时被 park 挂起，载体线程立即去跑其他虚拟线程；I/O 就绪后在任意可用载体上恢复。用同步写法获得异步性能。
  • 不适用场景：CPU 密集型任务（无法 park，白占载体）；大量使用 synchronized 的代码（pinning 问题——synchronized 块内挂起会把载体线程一起钉住，JDK 24 已改进；改造方案是换 ReentrantLock）。
Java
// 三种创建方式
Thread.startVirtualThread(() -> doWork());
Thread.ofVirtual().name("vt-").start(() -> doWork());
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    exec.submit(() -> doWork()); // 一任务一虚拟线程，不要池化复用！
}
// Spring Boot 3.2+ 一行开启：spring.threads.virtual.enabled=true
  • 面试话术：「线程池的存在是为了复用昂贵的平台线程；虚拟线程足够便宜，不需要池化，一任务一线程即可。限流改用信号量 Semaphore。」

1.2 Sealed Classes / Records / Pattern Matching

  • Record（16+）：不可变数据载体，自动生成构造器、getter、equals/hashCode/toString，替代 DTO 样板代码；类与字段均 final。
  • Sealed（17+）：sealed + permits 限定谁能继承/实现，配合模式匹配可实现穷尽性 switch（编译器校验，无需 default）。
  • Pattern Matching for switch（21+）：case Circle c -> ... 类型模式 + 解构，替代 instanceof 链与访问者模式。
  • 文本块（15+）：""" 多行字符串，写 JSON/SQL 不再需要转义。

1.3 Structured Concurrency 与 Scoped Values

  • Structured Concurrency（21 预览）：StructuredTaskScope 把一组并发子任务当作一个单元——任一失败整体取消、全部完成才返回，杜绝线程泄漏。
  • Scoped Values：虚拟线程时代替代 ThreadLocal 的方案，不可变、有明确作用域、内存友好。

2. 并发进阶（手写 AQS 是高频要求）

2.1 AQS 原理 ★

  • 全称 AbstractQueuedSynchronizer，JUC 锁与同步器的基座：ReentrantLock、CountDownLatch、Semaphore、ReentrantReadWriteLock 都基于它。
  • 核心三件套：volatile int state（同步状态）+ CLH 变体双向队列（排队等待线程）+ CAS（无锁修改 state）。
  • 独占模式流程：tryAcquire CAS 抢 state → 失败入队（Node 封装线程）→ LockSupport.park 挂起 → 前驱释放时 unpark 后继。
  • 共享模式：state 表示许可数，获取成功后传播唤醒后续共享节点（CountDownLatch、Semaphore）。

2.4 原子类、LongAdder 与 StampedLock

  • AtomicInteger 等基于 CAS 自旋；高并发下大量线程自旋失败，CPU 空转。
  • LongAdder：分段思想——base + Cell[] 分散热点，最终 sum 求和；高并发计数首选（缺点：sum 非强一致快照）。
  • StampedLock：读写锁升级版，支持乐观读（tryOptimisticRead 不阻塞写，读后 validate 校验票据），读多写少场景吞吐更高；不可重入。

2.5 CompletableFuture 编排

  • 串行 thenApply/thenCompose、并行汇聚 thenCombine/allOf、任一完成 anyOf/acceptEither。
  • 异常处理 exceptionally/handle；超时 orTimeout/completeOnTimeout（JDK 9+）。
  • 默认用 ForkJoinPool 公共池，生产环境务必指定业务线程池，避免被公共池拖累。

3. JVM 深入

3.1 类加载过程与对象创建细节

  • 类加载五阶段：加载 → 验证 → 准备（静态变量赋零值）→ 解析（符号引用转直接引用）→ 初始化（执行 clinit）。
  • 对象创建：类加载检查 → 分配内存（指针碰撞-内存规整 / 空闲列表-内存交错；并发安全靠 CAS+失败重试 或 TLAB 本地线程分配缓冲）→ 零值初始化 → 设置对象头（Mark Word、类型指针）→ 执行 init。
  • 逃逸分析：对象未逃逸出方法可栈上分配 + 标量替换，随栈帧销毁，减轻 GC 压力。

3.2 CMS / G1 / ZGC 对比与选型

3.3 线上问题排查四板斧 ★

  • CPU 飙高：top 找进程 → top -Hp pid 找线程 → printf %x 转 16 进制 → jstack pid | grep nid 定位代码行。常见原因：死循环、正则灾难回溯、频繁 GC。
  • Full GC 频繁：jstat -gcutil pid 1s 看各区占用 → jmap -histo 或 dump 后用 MAT 查支配树。常见原因：大对象、内存泄漏（ThreadLocal/静态集合/连接未关）、元空间不足。
  • 接口超时/抖动：Arthas trace 看方法耗时、watch 看入参出参；结合 GC 日志排除 STW。
  • 死锁：jstack 直接报 Found deadlock；或 Arthas thread -b 一键定位。

4. MySQL 深入

4.1 MVCC 原理 ★

  • 三要素：每行隐藏字段 DB_TRX_ID（最近修改事务 ID）、DB_ROLL_PTR（回滚指针，串起 undo log 版本链）、ReadView（读视图，含活跃事务列表 m_ids、min_trx_id、max_trx_id、creator_trx_id）。
  • 可见性判断：版本 trx_id < min_trx_id → 可见；≥ max_trx_id → 不可见；在 m_ids 中（仍活跃）→ 不可见，沿版本链继续找。
  • RC 与 RR 的区别：RC 每次 SELECT 生成新 ReadView；RR 只在事务第一次 SELECT 时生成一次——这就是 RR 可重复读的原因。
  • 当前读 vs 快照读：SELECT ... FOR UPDATE / LOCK IN SHARE MODE、增删改是当前读，读最新版本并加锁。

4.2 redo log / undo log / binlog 与两阶段提交

  • redo log（InnoDB，物理日志）：保证持久性，WAL 先写日志再刷盘，crash 后重放。
  • undo log：保证原子性 + 支撑 MVCC 版本链。
  • binlog（Server 层，逻辑日志）：主从复制与数据恢复。
  • 两阶段提交：redo prepare → 写 binlog → redo commit，保证崩溃恢复时两份日志一致，否则主从数据会不一致。

4.3 行锁、间隙锁与死锁

  • Record Lock 锁记录、Gap Lock 锁区间、Next-Key Lock（临键锁，左开右闭）= 记录 + 区间，RR 下默认，用于防幻读。
  • 加锁规则核心：锁加在索引上；没走索引的 UPDATE/DELETE 会锁全表（全记录 + 全间隙）。
  • 死锁排查：SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK；开启 innodb_print_all_deadlocks 记录全部死锁。
  • 避免死锁：固定加锁顺序、缩小事务、合理建索引、热点行拆分。

5. Redis 深入

5.1 底层数据结构

  • SDS：O(1) 取长度、二进制安全、预分配 + 惰性释放。
  • listpack（7.0 取代 ziplist）：紧凑存储小元素，解决连锁更新问题。
  • 跳表（ZSet）：多层索引，平均 O(log n) 查找，范围查询高效；不用红黑树是因为实现简单 + 范围遍历友好。
  • 渐进式 rehash：两个哈希表并存，每次增删改查顺带迁移一个桶，避免一次性迁移卡顿。

5.2 主从 / 哨兵 / Cluster

  • 主从复制：全量（RDB）+ 增量（repl_backlog 缓冲区）+ 命令传播。
  • 哨兵：监控、主观/客观下线、Raft 选 leader、故障转移、通知客户端。
  • Cluster：16384 个槽按 CRC16 分片，节点间 Gossip 交换信息；key 不在本节点返回 MOVED/ASK 重定向；槽位选择 16384 是心跳包大小与节点规模的权衡。

5.3 bigkey 与 hotkey 治理

  • 发现：--bigkeys 扫描、MEMORY USAGE、monitor 采样、代理层统计。
  • bigkey 危害：阻塞主线程（删除用 UNLINK 异步）、网卡打满、集群迁移慢。治理：拆分成多个小 key、压缩、避免大集合全量读取（HGETALL → HSCAN）。
  • hotkey 治理：本地缓存（Caffeine）兜底、key 打散加随机后缀读多份、读写分离。

5.4 分布式锁的正确姿势 ★

Java
// ❌ 面经常见反例：SETNX 和 EXPIRE 分两步，加锁后宕机 = 死锁
if (redis.setnx(key, "1")) { redis.expire(key, 30); }
// ✅ 正确：原子加锁（value 存唯一标识）+ Lua 原子解锁
SET lock_key uuid NX PX 30000
// 解锁 Lua：先 GET 比对 uuid 再 DEL，防止误删别人的锁
  • 业务超时锁到期怎么办：Redisson 看门狗——默认 30s 租约，每 10s 自动续期，直到显式 unlock 或宕机（宕机则自然过期）。
  • 可重入：Redisson 用 Hash 结构（field=线程标识，value=重入次数）。
  • 主从切换丢锁问题：官方红锁（RedLock）争议大，多数业务「Redis 锁 + DB 约束兜底」即可，金融级强一致再考虑 ZooKeeper/etcd。

6. Spring 深入

6.1 循环依赖与三级缓存 ★

  • 三级缓存：singletonObjects（成品 Bean）、earlySingletonObjects（提前暴露的半成品）、singletonFactories（ObjectFactory 工厂）。
  • A 依赖 B、B 依赖 A：A 实例化后先把 ObjectFactory 放入三级缓存 → 填充属性时发现依赖 B → 创建 B，B 填充属性时从三级缓存拿到 A 的早期引用 → B 完成 → A 完成。
  • 为什么需要三级而不是两级：ObjectFactory 可在获取时执行 AOP 代理逻辑，保证注入的是代理对象而非原始对象；两级缓存无法在「需要代理」和「不需要代理」间统一。
  • 无法解决：构造器注入循环依赖（实例化阶段就卡住）、prototype 循环依赖。

6.2 Spring MVC 请求处理流程

  • 请求 → DispatcherServlet → HandlerMapping 找 Handler → HandlerAdapter 适配执行 → 拦截器 preHandle → 参数解析（HandlerMethodArgumentResolver）→ 调用 Controller → 返回值处理（HandlerMethodReturnValueHandler / HttpMessageConverter）→ 拦截器 postHandle → 视图渲染或直接写响应。

6.3 Spring Boot 3.x 变化（新版必问）

  • 最低 JDK 17；javax.* → jakarta.* 命名空间迁移（老项目升级最大坑点）。
  • 自动配置注册文件从 spring.factories 迁移到 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports。
  • 支持虚拟线程（3.2+ 一行配置开启）与 GraalVM Native Image AOT 编译（启动毫秒级、内存大幅降低，代价是反射/动态代理需显式声明）。
  • 观测性一体化：Micrometer + OpenTelemetry 内置 Tracing/Metrics。

6.4 AI 工程化趋势：Spring AI 与 RAG

7.5 接口幂等设计

一、项目定位与技术栈

1.1 它是什么

Ragent 是一个面向 Agentic RAG 演进的企业级 RAG 平台，核心能力：

  • 多路检索：多渠道并行检索，去重重排兼顾精准与召回。
  • 意图识别：树形多级分类，置信度不足主动引导澄清；节点区分「知识库 / 系统应答 / 工具调用」三类。
  • 模型引擎：模型调度、首包探测、健康检查、自动降级，模型故障不影响服务。
  • MCP 集成：非知识类意图自动提参调用业务工具，检索与工具无缝融合。
它解决的不是「调个 API 就叫 RAG」，而是企业落地 RAG 真实会踩的坑：文档解析、分块策略、召回率、多路融合、幻觉控制、限流熔断、多租户隔离、可观测性。

三、核心业务流程链路：一次问答的全过程 ★重点

3.1 总览（流水线阶段编排）

入口：RAGChatController → RAGChatServiceImpl.streamChat()，主流程由 StreamChatPipeline（rag/service/pipeline/StreamChatPipeline.java）按阶段串联，采用「私有阶段方法 + boolean 短路返回」的轻量编排：

     ├─ 2. rewriteQuery(ctx)            // 问题改写 + 子问题拆分

     ├─ 4. handleGuidance(ctx)          // 歧义引导（置信度不足追问）

3.2 阶段 1：会话记忆加载

ConversationMemoryService.loadAndAppend 加载历史消息。难点不是「存」，而是记忆压缩：20 轮对话全塞给模型 Token 成本扛不住；只带最近几轮又可能丢关键信息。Ragent 用「滑动窗口 + 自动摘要压缩 + TTL 过期」平衡，避免长对话 OOM / Token 爆炸。

3.3 阶段 2：问题改写与子问题拆分

QueryRewriteService.rewriteWithSplit（及 MultiQuestionRewriteService）把用户口语 / 多轮上下文重写为规范子问题：

  • 用户输入「报销咋整」→ 改写为规范查询；
  • 多轮里说「怎么申请」→ 补上下文，否则系统不知道在问啥；
  • 复杂问题拆分为多个子问题分别检索，再融合。
  • 另有 QueryTermMappingService 做同义词 / 术语映射（如「墨盒」↔「墨盒更换」），提升召回。

3.4 阶段 3：意图识别（树形多级）

  • 意图节点 IntentNode：id / parentId / children / level / description / examples / kind，kind 分三类：
  • KB：走知识库检索；
  • SYSTEM：系统应答（直连 LLM，不走检索）；
  • MCP：调用业务工具。
  • 分类器 DefaultIntentClassifier：一次性把全部叶子节点喂给 LLM 打分（temperature=0.1），返回 List<NodeScore>，结果缓存于 Redis（IntentTreeCacheManager）。
  • 解析器 IntentResolver.resolve：按子问题并发分类，过滤 score >= INTENT_MIN_SCORE、上限 MAX_INTENT_COUNT，按 KB / MCP 拆成 IntentGroup。
  • 新增意图节点只需建库，IntentNodeRegistry 自动注册。

3.5 阶段 4：歧义引导

IntentGuidanceService + AmbiguityLLMChecker：当置信度不足时返回澄清提示，让用户补充信息，不直接检索。这是「RAG 常见误区」里强调的工程细节——走错路答案必错。

3.6 阶段 5：多路检索 ★

引擎 MultiChannelRetrievalEngine.retrieveKnowledgeChannels：

  • 检索通道接口 SearchChannel，实现类：
  • VectorSearchChannel（向量，内部按意图置信度二选一：命中库 IntentParallelRetriever / 全库 CollectionParallelRetriever）
  • KeywordSearchChannel（ES 关键词，精确匹配订单号等向量弱项）
  • WebSearchChannel（联网检索）
  • GraphSearchChannel（知识图谱，接 LightRAG）
  • 所有通道通过 CompletableFuture + ragRetrievalExecutor 线程池并行执行。
  • 后处理责任链（接口 SearchResultPostProcessor，按 getOrder() 排序）：
  • DeduplicationPostProcessor（去重）
  • FusionPostProcessor（多通道融合，RRF 倒数排名融合）
  • RerankPostProcessor（精排，调 RerankClient）
  • MetadataEnrichmentPostProcessor（元数据富化，补文档标题等）
纯向量检索对精确匹配很弱（用户问订单号找不到），所以必须混合检索 + 重排序。

3.7 阶段 6：Prompt 组装与流式输出

streamRagResponse 把检索到的上下文 + 会话记忆 + 系统提示组装成 Prompt，通过 SseEmitterSender（framework 提供的线程安全 SSE 封装）实时推送。RoutingLLMService 流式调用时用 ProbeStreamBridge + LlmFirstPacketProbe 做首包探测——首个模型首包超时即切换下一个，用户无感知。

全部在 infra-ai/.../model/ 与 infra/chat/：

多通道结果通过责任链逐步精炼：去重 → RRF 倒数排名融合 → 重排（RerankClient）→ 元数据富化。RerankClient 有 BaiLianRerankClient（通义）与 NoopRerankClient（空操作）两种实现。

6.3 向量库双支持

VectorStoreService 两个实现 MilvusVectorStoreService / PgVectorVectorStoreService；门面 VectorRetrieverService 支持 supportsGlobalRetrieval()（PG 单 SQL 跨库，Milvus 逐库 fan-out）。

七、意图识别体系

  • 意图树：IntentNode 多级分类，kind ∈ {KB, SYSTEM, MCP}，数据来自 IntentNodeMapper → 组装成树 → Redis 缓存。
  • 分类器：DefaultIntentClassifier 一次性 LLM 打分（温度 0.1）。
  • 解析器：IntentResolver.resolve 按子问题并发分类、过滤低分、按类型分组。
  • 注册表：IntentNodeRegistry 自动发现，新增意图零配置。
  • init_intent_node.sql 是意图树种子数据。

八、MCP 工具调用

mcp-server 是独立 Spring Boot 进程，暴露的工具（mcp/executor/，均注册为 McpServerFeatures.SyncToolSpecification）：

  • WeatherMcpExecutor（weather_query，城市天气）
  • SalesMcpExecutor（销售类业务工具）
  • TicketMcpExecutor（工单类工具）
  • YouComSearchMcpExecutor（You.com 搜索）

  • LLMMcpParameterExtractor：用 LLM 从问题提取工具参数（缺必填参 → 注入澄清提示让 LLM 追问，不调用）；
  • RetrievalEngine.executeMcpTools 按 mcpBatchExecutor 线程池并发调用，结果经 ContextFormatter.formatMcpContext 进入 Prompt。

11.1 队列式分布式限流

十五、关键机制深挖（源码级参数）

15.1 队列式限流的完整实现 ★

  • Redis 键族（前缀 rag:global:chat）：:semaphore（RPermitExpirableSemaphore 带租约许可）、:queue（ZSET，score=队列序号）、:queue:seq（RAtomicLong 发号器）、:queue:notify（Pub-Sub 唤醒）、:entry:<requestId>（存活标记，TTL=等待预算+5s 缓冲）。
  • Lua 脚本 resources/lua/queue_claim_atomic.lua：取队头窗口（maxRank+16 冗余），遍历中 EXISTS 校验存活标记，僵尸请求就地 ZREM 清理；存活名次在窗口内则原子出队并返回原 score（支持按原位次重入队）。
  • Ticket 状态机：PENDING → GRANTED / TIMED_OUT / CANCELLED，单 CAS 保证终态互斥；超时轮询间隔 200ms，PollNotifier 合并通知防惊群。
  • 默认参数（RAGRateLimitProperties）：max-concurrent=50、max-wait-seconds=20、permit 租约 lease-seconds=600（兜底防许可泄漏）。被拒时回写会话记忆并推送 REJECT 事件（文案「系统繁忙，请稍后再试」）。

15.2 RRF 融合与后处理责任链（精确参数）

  • 后处理器顺序（getOrder()）：去重 DeduplicationPostProcessor=1 → 融合 FusionPostProcessor=5 → 精排 RerankPostProcessor=10 → 元数据富化 MetadataEnrichmentPostProcessor=20。
  • RRF 公式（FusionPostProcessor.fuseByRrf）：score = Σ weight_channel / (k + rank + 1)，k 取配置 fusion.rrfK，各通道权重来自 fusion.channel-weights（vector / keyword / graph / webSearch / default）；融合后按 candidateLimit 截断再送 Rerank。
  • Rerank 链路：RerankPostProcessor → RoutingRerankService → RerankClient（BaiLianRerankClient / NoopRerankClient），总开关 rag.rerank-enabled。

15.3 模型熔断与首包探测（精确参数）

  • 三态熔断：CLOSED → OPEN（连续失败达 ai.selection.failureThreshold=2）→ 30s（openDurationMs=30000）后进 HALF_OPEN，半开只放单个探针，成功即闭合。
  • 流式容错：RoutingLLMService.streamChat 按 ModelSelector 给出的候选顺序逐个尝试，每个候选用 ProbeStreamBridge 包装回调，LlmFirstPacketProbe 以该模型 timeoutMs 为首包预算；ERROR / TIMEOUT / NO_CONTENT 一律 markFailure 并切换下一个，全部失败才 onError。
  • 降级顺序配置：ai.chat.tiers.<tier>.candidates 有序列表，顺序即降级顺序；分 defaultTier / deepThinkingTier 档位。

15.4 意图识别阈值与缓存

  • 阈值常量（RAGConstant）：INTENT_MIN_SCORE = 0.35、MAX_INTENT_COUNT = 3；分类采样 temperature=0.1 / topP=0.3 求稳。
  • IntentResolver 对子问题并行分类（intentClassifyExecutor），超限时「每子问题保底 1 个最高分 + 剩余按分数配额」。
  • 意图树缓存：Redis 键 ragent:intent:tree，TTL 7 天，节点增删改时主动失效。

15.5 会话记忆压缩参数

  • 配置前缀 rag.memory：historyKeepTurns=8（保留最近 8 轮原文）、summaryStartTurns=9（达到 9 条用户消息开始摘要）、summaryMaxChars=200、summaryEnabled 默认关闭。
  • 摘要覆盖约一半原文窗口（取中点 cutoff），滑出窗口后才重新生成；摘要调用用 Tier.FAST 档位模型、temperature=0.3。
  • 并发安全：摘要生成加分布式锁（键前缀 ragent:memory:summary:lock:），仅在 assistant 回复后异步触发。

四、工具定义 @tool

4.1 基础用法

  • 用 @tool 装饰普通函数即可把任意 Python 函数变成 Agent 可调用的工具；函数 docstring 即为工具描述（给模型看，务必写清楚）。
  • 类型注解会被自动转为 JSON Schema 入参；TypedDict / pydantic.BaseModel 可做更精细的结构化入参。
Python
from langchain.tools import tool

@tool
def get_weather(city: str, unit: str = "celsius") -> str:
    """查询指定城市的当前天气。

    Args:
        city: 城市名，如 "北京"
        unit: 温度单位，"celsius" 或 "fahrenheit"
    """
    return f"{city} 当前 25 度（{unit}），晴"

print(get_weather.name)        # "get_weather"
print(get_weather.args)        # {'city':..., 'unit':...} 自动生成的 JSON Schema

4.2 结构化入参与状态注入

  • 工具函数可用 InjectedState（from langchain.agents）注入运行时状态（如 context 或图状态），而不占用模型可见的入参。
  • 错误处理：工具内部抛异常会被框架捕获并作为「工具错误信息」回传给模型，让模型自行纠错重试，无需额外包装。
Python
from langchain.agents import InjectedState
from typing import Annotated

@tool
def reply_with_user(ctx: Annotated[dict, InjectedState("context")], msg: str) -> str:
    """把消息和当前登录用户名拼起来返回。"""
    return f"[{ctx['user_id']}] {msg}"

五、消息与标准内容块 content_blocks

5.1 content_blocks：跨供应商统一

  • 现代模型输出已从「纯字符串」演进为内容块列表：推理轨迹（reasoning）、引用（citations）、服务器端工具调用等。
  • v1.0 给消息新增 .content_blocks 属性，提供跨供应商一致的类型化视图；旧的 .content 字段保持完全向后兼容（仍是字符串或厂商原生结构）。
  • 支持的块类型：text、reasoning、image、audio、tool_call、citation 等。
Python
from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-5-mini")
resp = model.invoke("解释一下强化学习")

for block in resp.content_blocks:
    if block["type"] == "reasoning":
        print("思考：", block.get("reasoning"))
    elif block["type"] == "text":
        print("回答：", block.get("text"))

旧写法（v0）需针对每个厂商单独处理 reasoning / thinking 等字段，content_blocks 把这层差异抹平。

5.2 多模态消息

  • 通过 HumanMessage(content_blocks=[...]) 以标准化方式传入文本、图片、音频等，无需再写 OpenAI 风格 / Anthropic 风格两套结构。
  • 图片块可用 url（远程）或 data（base64）提供，并指定 mime_type。
Python
from langchain.messages import HumanMessage

msg = HumanMessage(content_blocks=[
    {"type": "text", "text": "描述这张图片"},
    {"type": "image", "url": "https://example.com/cat.png", "mime_type": "image/png"},
])
res = model.invoke([msg])

六、构建智能体 create_agent

6.1 最小可运行的 Agent

  • create_agent(model, tools, prompt/system_prompt) 是 v1.0 推荐的唯一起点，替代旧 AgentExecutor 与 langgraph.prebuilt.create_react_agent。
  • 返回的 agent 是一个 LangGraph 编译后的图，支持 .invoke() / .stream() / .ainvoke()。
Python
from langchain.agents import create_agent
from langchain.chat_models import init_chat_model
from langchain.tools import tool

@tool
def add(a: int, b: int) -> int:
    """把两个数相加。"""
    return a + b

model = init_chat_model("openai:gpt-4o-mini")
agent = create_agent(model, tools=[add], prompt="你是一个爱用中文的计算助手。")

result = agent.invoke({"messages": [{"role": "user", "content": "3 加 5 等于多少？"}]})
print(result["messages"][-1].content)

Node.js 等价写法：import { createAgent } from "@langchain/langchain"。

6.2 system_prompt 与运行时 context

  • v0 用 prompt 参数；v1 推荐用 system_prompt，并支持 SystemMessage 实例。
  • 静态上下文（如 user_id、session_id，整轮对话不变）通过 context 参数注入，配合 context_schema 声明结构；动态对话状态仍是 messages。旧 config["configurable"] 方式保留兼容。
Python
from dataclasses import dataclass
from langchain.agents import create_agent

@dataclass
class Context:
    user_id: str
    session_id: str

agent = create_agent(model, tools=[add], context_schema=Context)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "你好"}]},
    context=Context(user_id="123", session_id="abc"),
)

6.3 流式调用

  • agent.stream(...) 逐块产出消息增量（含工具调用与最终文本），适合做打字机式 UI。
  • 每个流式事件含 messages 列表，用法与 invoke 一致，只是分多次返回。
Python
for chunk in agent.stream({"messages": [{"role": "user", "content": "讲个冷笑话"}]}):
    for m in chunk.get("messages", []):
        if hasattr(m, "content") and m.content:
            print(m.content, end="", flush=True)

七、智能体中间件 Middleware

7.1 内置中间件

  • 中间件是可插拔的钩子，挂在 Agent 循环的每一步，替代以前「子类化 + 自己包一层」的写法。
  • 内置三件套：
    • Human-in-the-loop：关键步骤暂停，等待人工审批 / 修改。
    • Summarization（摘要）：自动压缩历史对话，防止上下文溢出（1.1 起利用 model profile 更聪明地决策）。
    • PII Redaction（隐私擦除）：内容传递前自动脱敏敏感信息。
  • 1.1 额外提供：OpenAI Moderation 中间件、内置带退避的模型重试。
Python
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoop, Summarization

agent = create_agent(
    model, tools=[transfer_money],
    middleware=[
        HumanInTheLoop(tools=["transfer_money"]),   # 转账前人工确认
        Summarization(threshold=20),                    # 超过 20 条消息自动摘要
    ],
)

7.2 自定义中间件

  • 实现中间件协议（提供 init / process_model_input / process_model_output 等钩子）即可在循环任意阶段插入逻辑，比如日志、限流、二次校验。
  • 钩子粒度：进入模型前改写输入、模型返回后改写输出、工具调用前/后拦截。

八、结构化输出 Structured Output

8.1 response_format + ToolStrategy

  • v1.0 把结构化输出生成整合进主 Agent 循环，不再额外多调一次 LLM，降低延迟与成本。
  • 用 response_format 指定 pydantic 模型 + 策略（ToolStrategy 走工具调用，或厂商原生 structured output），让模型最终输出强类型对象。
Python
from langchain.agents import create_agent
from langchain.agents.structured_output import ToolStrategy
from pydantic import BaseModel

class WeatherReport(BaseModel):
    temperature: float
    condition: str

agent = create_agent(
    "openai:gpt-4o-mini",
    tools=[get_weather],
    response_format=ToolStrategy(WeatherReport),
    prompt="请查天气并以结构化报告返回。",
)

report = agent.invoke({"messages": [{"role": "user", "content": "北京天气？"}]})
print(report.structured_response)   # WeatherReport(temperature=25.0, condition="晴")

8.2 厂商原生结构化输出

  • 若厂商支持原生 structured output（如 OpenAI / Anthropic），可改用原生策略以获得更好性能；跨厂商统一则用 ToolStrategy 兜底。
  • 细粒度控制权：开发者可决定「用工具调用」还是「厂商原生」，框架在 Agent 循环内统一收敛。

九、持久化与 LangGraph 运行时

9.1 Durable State 与断点恢复

  • LangGraph 是 LangChain 的底层运行时，提供持久化状态：Agent 执行状态自动落盘，服务器重启或长任务中断后可从断点精确恢复，用户无需重来。
  • 内置持久化：通过 checkpointer 保存/恢复任意时刻的工作流，无需手写数据库逻辑，支持多天审批、跨会话后台任务。
  • 用法：给 agent 传入 checkpointer=MemorySaver()（演示）或 PostgresSaver（生产），并在调用时带 thread_id。
Python
from langgraph.checkpoint.memory import MemorySaver

agent = create_agent(model, tools=[add], checkpointer=MemorySaver())
cfg = {"configurable": {"thread_id": "sess-1"}}

agent.invoke({"messages": [{"role": "user", "content": "记住我叫小明"}]}, cfg)
# 下次同一 thread_id 调用会带着上轮记忆继续

9.2 人在回路 HITL

  • LangGraph 对「暂停 → 人工审查 / 修改 / 批准」提供一等公民 API，配合上一节中间件可轻松构建高风险决策的人类兜底。
  • 典型流程：agent 跑到需审批节点 → 暂停并等待人类输入 → resume 带批准结果继续。

📌 Embabel Agent · 版本 0.x · 最后更新 2026-08-06

Embabel Agent 知识库（JVM 上的目标导向智能体框架）

Embabel（发音 Em-BAY-bel）是由 Spring Framework 创始人 Rod Johnson 打造的 JVM 智能体框架，构建于 Spring AI 之上，用 Kotlin 编写但对 Java 极其友好。它的核心主张是：用非 LLM 的确定性规划算法（GOAP/A*）动态编排 Actions，把 LLM 调用与普通 JVM 代码、强类型领域模型无缝混合，从而得到「可解释、可调试、可重构」的智能体。本知识库基于官方文档 docs.embabel.com 与 GitHub 仓库整理，答法遵循「概念 → 注解 → 代码 → 原理 → 坑点」。

一、定位与背景

1.1 它解决什么问题

  • 绝大多数 Agent 框架活在 Python 生态；JVM 开发者要么调用 Python 服务，要么在裸 LLM 客户端上手写编排逻辑。
  • LangChain 等依赖 LLM 做路由决策，非确定性、难调试；Embabel 用经典 AI 规划（非 LLM）决定「下一步执行哪个 Action」。
  • 目标：成为在 JVM（尤其是 Spring 应用）上做 GenAI 的「自然方式」，证明模型能力，并逐步演化为「自然语言 PaaS」。

1.2 与 Spring AI / LangChain 的关系

维度Spring AIEmbabelLangChain(1.0)
定位AI 集成基础库（ChatClient/VectorStore/Tool）构建于 Spring AI 之上的智能体编排框架智能体抽象（create_agent）
规划方式无（由你写流程）GOAP/A* 确定性规划 + 每步 ReplanLangGraph 图执行
强类型POJO 映射输出全程强类型领域模型驱动TypedDict / pydantic
语言Java/KotlinKotlin 为主，Java 友好Python / JS

二、核心概念

2.1 五大支柱

  • Actions：智能体执行的离散步骤（一个方法），可调用 LLM、工具或普通代码。
  • Goals：智能体要达成的目标，由系统动态推导，而非硬编码。
  • Conditions：执行 Action 前需满足的前置条件、以及判定 Goal 是否已达成的后置条件；每个 Action 后都会重新评估。
  • Domain Model：支撑流程的强类型领域对象，为 Actions/Goals/Conditions 提供类型信息。
  • Plan：由系统用非 LLM 算法动态编排出的一组 Action 序列；每完成一个 Action 就重新规划（OODA 循环）。

2.2 为什么「不用 LLM 做规划」是关键差异

  • 确定性：规划是经典 AI 算法（A*/GOAP），可解释、可调试、成本极低，不消耗 token。
  • 可扩展：新增 Action/Goal/Condition 即可扩展系统能力，无需改现有的状态机或代码。
  • 强类型：提示词与手写代码通过领域模型干净交互，没有「魔法 Map」，享受完整重构支持。
  • 平台抽象：编程模型与运行时解耦，本地可跑，生产可上更高 QoS 而不改应用代码。

七、规划引擎（GOAP / A*）

7.1 工作原理

  1. Goal Resolver：把用户意图映射到最匹配的目标。
  2. Planning Engine：用非 LLM 的 A* 算法在「当前世界状态」与「目标」之间搜索最优 Action 序列——这是经典 AI 规划，不是让 LLM 决定下一步。
  3. OODA 循环：Observe → Orient → Decide → Act。每执行一个 Action 后重新评估 Conditions 并重新规划，从而对新信息做出反应。
  4. Blackboard：各 Action 的输入/输出对象挂在 Blackboard 上，规划器据此串接（类型 A 产出 → 类型 B 消费）。

7.2 为什么不是状态机

  • 有限状态机 / 线性链是「写死的流程」；Embabel 是「已知步骤的新组合」，能完成从未显式编程的任务。
  • 新增领域对象、Action、Goal、Condition 即可扩展能力，无需改 FSM 定义或既有代码。

八、工具与 ToolGroup

8.1 声明工具组

Action 用 toolGroups 声明运行所需工具；ToolGroup.WEB 等标准组由框架/扩展提供。工具也可通过领域对象上的 @Tool 方法暴露（见 4.2）。

8.2 安全提示

  • 即使最好的 LLM 也可能「手痒」乱触发工具，对会改数据/删数据的方法要特别谨慎。
  • 更稳妥的做法：把危险操作建模为同一领域类上的非工具方法，在代码 Action 里显式调用。

十四、最佳实践与常见坑

14.1 实践清单

  • 类型优先：所有 LLM 输出尽量映射为 record/data class，享受重构与强类型。
  • LLM 只做它擅长的：抽取、生成、判断用 LLM；查库、计算、校验用确定性代码。

  • 从 start.spring.io 勾选模型/向量库即可一键 bootstrap。

十八、最佳实践与常见坑

18.1 实践清单

  • 以 ChatClient 为入口：不要直接调 ChatModel，让 advisor 链、工具注册、流式支持一肩挑。
  • System Prompt 优先于换模型：用清晰的角色/边界/工具规则/system prompt 往往比换模型更有效、更省钱。
  • 结构化输出用 record + @JsonClassDescription：稳定拿到强类型结果。
  • RAG + 工具组合时给模型指引：明确「何时用上下文、何时用工具」。
  • 控制工具数量与记忆窗口：工具过多会稀释模型决策；记忆窗口按需裁剪控制 token。
  • 加可观测性：生产环境务必开启评估与日志，及时发现幻觉/越界。

后端业务项目开发模板（以 Ragent 为蓝本）

零、开篇：拿到一个后端业务项目，从哪里开始？

很多人一上来就「先堆 CRUD、再补功能」，结果越写越乱、越改越怕。正确的顺序是先想清楚、再动手：需求 → 选型 → 架构 → 实现 → 运维 五个阶段闭环推进，而不是一条直线冲到底。本库以「Ragent（一个 AI 智能问答 / 知识库系统）」为蓝本，把一个真实业务项目从 0 到 1 该考虑的每件事拆给你看——既能当方法论，也能当检查清单。

阶段核心问题产出物
① 需求到底要解决谁的什么问题？做到什么程度算成功？功能清单 + 非功能指标 + MVP 边界
② 选型在团队 / 成本 / 性能 / 可维护的约束下，用什么？技术选型表（含备选与理由）
③ 架构模块怎么分、依赖怎么走、数据怎么流？分层图 + 模块边界 + 时序
④ 实现每个功能点落地时，技术的优缺点怎么权衡？逐功能技术拆解 + 取舍记录
⑤ 运维怎么上线、怎么扛量、出事怎么查？部署拓扑 + 监控 + 上线 Checklist
记住一句总纲：「先定约束，再选技术；先分边界，再写代码；先能跑通，再谈优雅。」

一、阶段一：需求梳理与范围界定

1.1 功能需求：用「用户故事」拆，而不是用「我要做个系统」

  • 每个功能写成 作为<角色>，我希望<动作>，以便<价值>。例：作为访客，我希望输入问题得到流式回答，以便像聊天一样获取知识。
  • 功能要能验收：能写出「满足 X 条件即算通过」的测试标准，否则等于没需求。
  • 功能要可排优先级：用 MoSCoW（Must / Should / Could / Won't）区分，避免一上来全做。

1.2 非功能需求（NFR）：决定技术难度的往往是它

维度要问的问题典型指标
性能单次请求多久要回？P95 < 800ms（首包 < 1.5s）
并发同时多少人用？峰值 200 QPS / 全局 50 并发
可用性挂了多久能恢复？99.9%（月停 < 43 分钟）
安全谁能用、数据归谁？登录鉴权 + 多租户隔离
合规数据要存境内吗？等保 / 数据不出境
可演进半年后要不要加能力？插件化 / 配置化预留

1.3 以 Ragent 模拟：需求怎么拆

  • Must：问答接口（流式）、知识库上传与检索、用户登录。
  • Should：意图识别、多路混合检索、限流防刷、会话记忆。
  • Could：文档定时刷新、MCP 外部工具、Rerank 精排。
  • Won't（本期不做）：多模态图文问答、私有化小模型微调。
「Won't」和「Must」一样重要——它帮你挡住无底洞需求，保护 MVP 能按时上线。

二、阶段二：技术选型的总原则

2.1 先定约束，再选技术

  • 团队约束：团队只会 Java？就别硬上 Go/Rust；只会单体？先别强上微服务。
  • 成本约束：云上 GPU 推理很贵，能走 API 就别自建集群。
  • 性能约束：要毫秒级检索？就得上向量索引，不能靠 LIKE 全表扫。
  • 可维护约束：招不到人维护的技术栈，再先进也不能碰。

2.2 自研 vs 开源 vs 云服务的权衡

路径优点缺点何时选
直接用云服务（如大模型 API）零运维、弹性、上线快长期成本高、锁定、数据出境风险MVP / 不确定规模时
用成熟开源（如 Spring AI / LangChain）可控、社区活跃、可改要自己集成、踩坑有定制需求、团队能 hold 住
完全自研（如 Ragent 的 infra-ai）完全贴合业务、无依赖绑架成本高、需长期养核心差异化能力、已有沉淀

2.3 选型要留「演进后路」

  • 抽象一层接口，底层可替换：今天用 DeepSeek，明天换通义，业务代码不动。
  • 配置驱动：开关、阈值、权重都放配置，不写死在代码里。

4.1 对话问答核心链路：SSE 还是 WebSocket？

方案优点缺点适用
SSE（Server-Sent Events）基于 HTTP、天然断线重连、单向推送简单、好过代理只能服务端→客户端单向；二进制弱AI 流式回答（Ragent 选它）
WebSocket全双工、双向实时、可传二进制需自己管心跳/重连、代理/CDN 支持参差协同编辑、聊天室、游戏
普通轮询实现最简单延迟高、空转浪费极简场景、临时方案
  • 取舍：AI 回答是「服务端一直推、客户端只发一次问题」，SSE 最契合；还要支持「中途停止」，用单独的 POST /stop 接口即可，不必为双向而 WebSocket。

4.2 并发限流：队列式限流 vs 令牌桶

方案优点缺点
令牌桶 / 漏桶（Guava / Redis）实现简单、平滑限平均速率突发时直接拒绝，用户体验差；不保证「先到先服务」
信号量 + 排队（Ragent 队列式）满负载时排队等待而非拒绝，公平且体验好实现复杂（需 Lua 原子出队、僵尸清理、超时状态机）
  • 参数示例：全局并发 50、排队上限 20s、许可租约 600s 兜底防泄漏；被拒回写记忆并推「系统繁忙」。
  • 何时选队列：下游（LLM）是稀缺资源、且希望用户「等一下而非直接失败」；何时选令牌桶：纯接口防刷、不在乎个别请求失败。
Java · 令牌桶 vs 队列式（最小可运行）4.2
// 令牌桶（Guava RateLimiter）：拿不到立即拒绝
RateLimiter rl = RateLimiter.create(50.0);     // 50 许可/秒
if (rl.tryAcquire()) handle(req);
else reject429(req);

// 队列式（Ragent）：满则进带 TTL 的队列等待，而非拒绝
if (semaphore.tryAcquire(20, SECONDS)) {       // 20s 排队上限
    try { handle(req); }
    finally { semaphore.release(); }
} else { reject429(req); }                       // 仍超限才拒绝

4.3 检索增强（RAG）：向量 / 关键词 / 混合，怎么选？

检索方式优点缺点典型用
向量检索（Embedding + 近似近邻）语义匹配强，问法不同也能命中精确值/专名弱；依赖 Embedding 质量口语化、语义相似问题
关键词检索（ES / 倒排）精确匹配、专名/编号准、可解释同义/泛化能力差订单号、术语、法规条文
混合检索（多路并行 + RRF 融合）兼顾语义与精确，召回更全链路更长、要调权重与融合参数生产级知识库（Ragent 选它）
Rerank 精排在召回基础上重排，相关性更高额外一次模型调用、有成本候选多、要保 Top 质量时开启
  • RRF 融合公式：score = Σ weight / (k + rank + 1)；各通道权重可配（vector/keyword/graph/web），融合后截断再送 Rerank。
  • 取舍：MVP 先上向量检索跑通；召回不够再补关键词；质量不稳再加 Rerank——逐级加复杂度。
算法 · RRF 融合（最小可运行）4.3
// 多通道召回按排名倒数求和，再截断送 Rerank
double scoreOf(String docId) {
    double s = 0;
    for (Channel ch : channels) {               // vector / keyword / graph ...
        int rank = ch.rankOf(docId);            // 1-based 排名
        s += ch.weight / (60 + rank);           // k = 60 平滑
    }
    return s;
}

  • 参数：意图阈值 0.35、最多 3 个意图、temperature=0.1/topP=0.3 求稳；结果缓存 7 天减少重复调用。

4.5 会话记忆与上下文压缩

  • 不压缩：实现简单，但长对话爆 token、贵且慢。
  • 滑动窗口（保留最近 N 轮）：简单有效，但会丢早期上下文。
  • 摘要压缩（Ragent）：保留 8 轮原文 + 超 9 轮开始摘要（≤200 字）；优点是不丢全局背景，缺点是异步摘要有延迟、要分布式锁防并发。
  • 取舍：MVP 用滑动窗口；对话长、要连续性的业务再上摘要。Ragent 默认关摘要，按需开。
算法 · 滑动窗口 + 摘要压缩（最小可运行）4.5
List<Turn> recent = history.tail(8);          // 保留最近 8 轮原文
if (history.size() > 9) {
    String summary = cache.getOrLock(userId, () ->  // 分布式锁防并发
        llm.summarize(history.except(recent), 200)); // 超 9 轮开始摘要，≤200 字
    prompt = concat(summary, recent);
} else {
    prompt = concat(recent);                    // 否则直接用原文
}

4.6 模型路由与容错：多模型 / 熔断 / 降级 / 首包探测

机制解决什么要点
多模型路由不同任务用不同模型（快/贵）分 defaultTier / deepThinkingTier 档位
熔断（三态）某模型连续失败不再傻等连续失败 2 次→OPEN 30s→半开放探针

首包探测流式过程中某个模型不吐字就换按各模型 timeoutMs 探测，ERROR/TIMEOUT 即切下一个
  • 取舍：单模型能跑通就别上全套容错；当依赖外部 LLM API（不稳定）时，熔断+降级是必选项而非可选项。

for (Model m : candidates) {                  // 候选顺序即降级顺序

}
return fallbackAnswer();                        // 全部失败→降级回复

消息队列（MQ）知识体系

零、开篇：为什么需要消息队列

消息队列（Message Queue，简称 MQ）是一个跨进程的异步通信中间件：生产者把消息放进队列就返回，消费者按自己的节奏异步取走处理。它解决的不是「传输」，而是「解耦、异步、削峰」三件事。

它能解决的问题说明反例（不用 MQ 会怎样）
应用解耦上游只管发消息，不关心谁消费；下游增减不影响上游下单直接调库存/积分/短信，一处挂全部超时
异步提速非核心链路（发短信、记日志）异步处理，主流程更快返回下单要等所有同步调用完成才返回
流量削峰突发流量先堆积在队列，消费者按能力匀速处理秒杀瞬时流量直接打垮数据库
可靠传递配合 ACK / 重试 / 死信，保证消息不丢同步调用失败即丢失，无兜底
一句话总纲：「能异步的别同步，能解耦的别直连，能削峰的别硬扛。」但 MQ 不是银弹——它带来一致性、时延、运维复杂度，能用同步简单解决的就不要硬上 MQ。

一、核心概念与术语

术语含义
Producer / 生产者发送消息的一方
Consumer / 消费者接收并处理消息的一方
Broker消息服务器，负责存储与转发（Kafka/RocketMQ 叫 Broker，RabbitMQ 叫节点）
Topic / 主题消息的逻辑分类（发布订阅模型的「频道」）
Queue / 队列消息的物理存储（点对点模型里消费者从队列取）
Exchange（RabbitMQ）接收生产者消息并按规则路由到队列的组件
Partition / 分区（Kafka/RocketMQ）一个 Topic 被切成多个分区，是并行度与顺序性的基本单位
Consumer Group / 消费组同一组内的消费者竞争消费一个 Topic（实现负载均衡与广播的区分）
Offset / 消费位点消费者在分区上的消费进度；提交 offset 即「已消费」的凭证
ACK消费者处理成功后向 Broker 回执，Broker 才认为消息消费成功

三、消息模型：点对点 vs 发布订阅

模型机制特点适用
点对点（P2P / Queue）一条消息只被一个消费者消费，消费后出队竞争消费、负载均衡、天然去重任务分发、工单、异步作业
发布订阅（Pub/Sub / Topic）一条消息被所有订阅者收到一对多广播事件通知、缓存失效广播
  • 消费组的作用：同一消费组内成员竞争消费（实现 P2P 的负载均衡）；不同消费组之间互不影响、各自全收（实现 Pub/Sub 的多播）。Kafka/RocketMQ 用「消费组 + 组内分区分配」一个模型统一表达两种语义。

四、投递语义：三条保证怎么选

语义含义实现代价
At-Most-Once（最多一次）可能丢，绝不重最低：发了不确认即可
At-Least-Once（至少一次）不丢，可能重中：ACK + 重试；消费端须幂等
Exactly-Once（精确一次）不丢不重最高：事务消息 + 幂等 / 分区原子写
  • 现实建议：绝大多数业务做到 At-Least-Once + 消费幂等 即可（Kafka 默认语义），性价比最高。
  • 幂等怎么写：用「业务唯一键 + 去重表 / 数据库唯一索引 / Redis SETNX」拦截重复消息；例如订单号作唯一键，重复消费直接跳过。
  • Exactly-Once 何时上：金融对账、金额变动等「重一次就出钱」的场景；Kafka 靠事务 + 幂等 producer，RocketMQ 靠事务消息 + 回查。

五、消息顺序性

  • 全局有序：整个 Topic 只有一个分区/队列 → 吞吐受限，几乎不用。
  • 分区有序（常用）：同一业务主键（如订单号）哈希到同一分区，分区内 FIFO；不同主键之间无序，但单key有序。
  • 实现要点：生产者用「相同 key → 相同 partition」的路由；消费者单线程消费该分区；Broker 故障切换时可能短暂乱序，需配合业务幂等兜底。

六、RabbitMQ 深入：AMQP 与四种 Exchange

RabbitMQ 的核心在 Exchange 按绑定规则把消息路由到 Queue。生产者只发给 Exchange，不直接碰 Queue。

Exchange 类型路由规则适用
DirectroutingKey 完全相等才投递定向分发（如按业务类型）
TopicroutingKey 按 . 分隔，# 多段、* 单段通配灵活多条件订阅
Fanout忽略 key，广播到所有绑定队列缓存失效、事件通知
Headers按消息头键值对匹配（忽略 key）结构化属性路由（较少用）
  • 死信交换机（DLX）：队列可设 x-dead-letter-exchange，消息被拒绝 / 过期 / 队列满时自动转入死信队列，用于隔离异常消息做人工处理。
  • 缺点：Erlang 栈运维门槛高；集群镜像队列有性能损耗；超高吞吐不如 Kafka。

七、Kafka 深入：分区、消费组、Offset、ISR

  • 分区（Partition）：Topic 的物理分片，并行度与顺序性的最小单位；分区数决定最大消费并行度。
  • 消费组 + 分区分配：一个分区同一时刻只被组内一个消费者持有；消费者数 > 分区数时多余消费者空闲。
  • Offset：消费者在分区上的进度；自动提交简单但有丢失/重复风险，手动提交（处理完再 commit）更可靠。
  • ISR（In-Sync Replicas）：与 Leader 保持同步的副本集合；Leader 挂了从 ISR 选新 Leader，保证不丢已提交消息。
  • 零拷贝（sendfile）：Kafka 顺序写盘 + 零拷贝读，是高吞吐的根因。
  • 日志压缩（Log Compaction）：同一 key 只保留最新 value，适合「状态/配置」类变更流。

八、RocketMQ 深入：架构、Tag、事务与顺序消息

  • 架构：NameServer（路由注册中心，无状态）+ Broker（存消息，主从）+ Producer/Consumer。比 Kafka 多一层 NameServer 做服务发现。
  • Tag：Topic 下的二级分类，消费时可按 Tag 过滤（如 order CREATE|PAY），同一 Topic 内做细分订阅。
  • 事务消息：Half Message（半消息）→ 执行本地事务 → 提交/回滚；Broker 定时回查事务状态，保证「本地事务与消息发送」最终一致（解决「下单成功但消息没发」）。
  • 延迟消息：内置 18 个延迟级别（1s~2h），无需自己轮询。
  • 顺序消息：局部顺序（同一 sharding key 进同一队列）用 MessageQueueSelector 指定队列；全局顺序基本不用。
  • 重试 / 死信：集群消费失败自动重试（默认 16 次），超限进 %DLQ% 死信队列。

九、Pulsar 速览：分层架构与 BookKeeper

  • 分层：Broker 无状态（只管服务与路由）+ BookKeeper 存数据（分段存储在 Bookie 上），二者解耦，扩缩容互不影响。
  • 优势：存算分离 → 弹性扩缩容；分层存储（冷数据沉到对象存储）降低长期成本；原生多租户隔离。
  • Subscription 类型：Exclusive / Shared / Failover / Key_Shared，覆盖独占、共享、按 key 保序等多种消费模式。
  • 取舍：功能最现代，但组件多（ZK+BookKeeper+Broker）、运维最重，中小团队未必需要。

十、可靠性保障：ACK / 重试 / 死信 / 幂等

风险应对
消费失败不提交 offset / 不 ACK，触发重试（有限次）
反复失败（毒消息）超限进死信队列（DLQ）隔离，人工排查，不阻塞主队列
重复消费消费端幂等：唯一键 + 去重表 / 唯一索引 / Redis SETNX
消息丢失（生产侧）发送确认（Kafka acks=all；RocketMQ 同步发送 + 刷盘）
消息丢失（Broker 侧）多副本 + 刷盘策略（同步刷盘最稳但慢）
消息丢失（消费侧）先处理业务、再提交 offset（别「先提交后处理」）
防丢三道防线：生产确认 → Broker 多副本/刷盘 → 消费先处理后提交。任意一环偷懒都可能丢。

十一、高可用与集群

  • RabbitMQ：镜像队列（mirror queue）做冗余，节点故障切换；3.8+ 推 Quorum Queue 更稳。
  • Kafka：每个分区多副本（replication-factor≥3），Leader 挂从 ISR 选；Controller 管分区选举。
  • RocketMQ：多 Master + 多 Slave（同步双写），Broker 故障从节点接管；NameServer 多节点互不可知、各自注册。
  • 通用原则：副本数 ≥ 3；跨机架/可用区部署；监控副本同步与 Leader 分布，避免热点。

十二、消费模式：Push vs Pull

模式谁主动优点缺点
Push（RabbitMQ 默认）Broker 推给消费者实时性强、时延低消费者易被压垮，需限流（prefetch）
Pull（Kafka/RocketMQ 默认长轮询）消费者主动拉消费速率自控、背压友好实现略复杂，靠长轮询兼顾实时
  • 长轮询（long-polling）：消费者拉取时 Broker 若无消息则「挂起」一小段时间再返回，兼顾 Pull 的自控与 Push 的实时，是 Kafka/RocketMQ 的折中方案。

十四、最佳实践清单

  • 消息体别太大（建议 < 1MB；大文件走对象存储，消息只存 URL）。
  • 消息设计幂等消费，把「至少一次」当默认假设。
  • 关键链路用同步发送 + 发送确认，非关键可异步。
  • 消费逻辑先处理业务再提交 offset，顺序别反。
  • 为有失败风险的消息配重试 + 死信队列。
  • 监控三件套：生产成功率、消费 lag、死信量。
  • Topic / 分区数提前规划，后期扩容分区会让已有 key 路由变化（谨慎）。
  • 敏感消息加密 / 脱敏，传输用 TLS。
