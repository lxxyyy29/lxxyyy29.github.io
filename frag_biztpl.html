后端业务项目开发模板（以 Ragent 为蓝本）

零、开篇：拿到一个后端业务项目，从哪里开始？

很多人一上来就「先堆 CRUD、再补功能」，结果越写越乱、越改越怕。正确的顺序是先想清楚、再动手：需求 → 选型 → 架构 → 实现 → 运维 五个阶段闭环推进，而不是一条直线冲到底。本库以「Ragent（一个 AI 智能问答 / 知识库系统）」为蓝本，把一个真实业务项目从 0 到 1 该考虑的每件事拆给你看——既能当方法论，也能当检查清单。

阶段核心问题产出物
① 需求到底要解决谁的什么问题？做到什么程度算成功？功能清单 + 非功能指标 + MVP 边界
② 选型在团队 / 成本 / 性能 / 可维护的约束下，用什么？技术选型表（含备选与理由）
③ 架构模块怎么分、依赖怎么走、数据怎么流？分层图 + 模块边界 + 时序
④ 实现每个功能点落地时，技术的优缺点怎么权衡？逐功能技术拆解 + 取舍记录
⑤ 运维怎么上线、怎么扛量、出事怎么查？部署拓扑 + 监控 + 上线 Checklist
记住一句总纲：「先定约束，再选技术；先分边界，再写代码；先能跑通，再谈优雅。」

一、阶段一：需求梳理与范围界定

1.1 功能需求：用「用户故事」拆，而不是用「我要做个系统」

  • 每个功能写成 作为<角色>，我希望<动作>，以便<价值>。例：作为访客，我希望输入问题得到流式回答，以便像聊天一样获取知识。
  • 功能要能验收：能写出「满足 X 条件即算通过」的测试标准，否则等于没需求。
  • 功能要可排优先级：用 MoSCoW（Must / Should / Could / Won't）区分，避免一上来全做。

1.2 非功能需求（NFR）：决定技术难度的往往是它

维度要问的问题典型指标
性能单次请求多久要回？P95 < 800ms（首包 < 1.5s）
并发同时多少人用？峰值 200 QPS / 全局 50 并发
可用性挂了多久能恢复？99.9%（月停 < 43 分钟）
安全谁能用、数据归谁？登录鉴权 + 多租户隔离
合规数据要存境内吗？等保 / 数据不出境
可演进半年后要不要加能力？插件化 / 配置化预留

1.3 以 Ragent 模拟：需求怎么拆

  • Must：问答接口（流式）、知识库上传与检索、用户登录。
  • Should：意图识别、多路混合检索、限流防刷、会话记忆。
  • Could：文档定时刷新、MCP 外部工具、Rerank 精排。
  • Won't（本期不做）：多模态图文问答、私有化小模型微调。
「Won't」和「Must」一样重要——它帮你挡住无底洞需求，保护 MVP 能按时上线。

二、阶段二：技术选型的总原则

2.1 先定约束，再选技术

  • 团队约束：团队只会 Java？就别硬上 Go/Rust；只会单体？先别强上微服务。
  • 成本约束：云上 GPU 推理很贵，能走 API 就别自建集群。
  • 性能约束：要毫秒级检索？就得上向量索引，不能靠 LIKE 全表扫。
  • 可维护约束：招不到人维护的技术栈，再先进也不能碰。

2.2 自研 vs 开源 vs 云服务的权衡

路径优点缺点何时选
直接用云服务（如大模型 API）零运维、弹性、上线快长期成本高、锁定、数据出境风险MVP / 不确定规模时
用成熟开源（如 Spring AI / LangChain）可控、社区活跃、可改要自己集成、踩坑有定制需求、团队能 hold 住
完全自研（如 Ragent 的 infra-ai）完全贴合业务、无依赖绑架成本高、需长期养核心差异化能力、已有沉淀

2.3 选型要留「演进后路」

  • 抽象一层接口，底层可替换：今天用 DeepSeek，明天换通义，业务代码不动。
  • 配置驱动：开关、阈值、权重都放配置，不写死在代码里。

三、阶段三：总体架构设计

3.1 经典四层（自顶向下）

层职责Ragent 对应
接入层路由、鉴权、限流、协议转换（HTTP/SSE/WS）Nginx + Controller + Sa-Token + RateLimiter
业务层编排用例、领域逻辑Service + Pipeline + Intent
能力层模型、检索、存储等通用能力infra-ai / Retrieval / Ingestion
基础设施DB / 缓存 / MQ / 对象存储PostgreSQL+PGVector / Redis / RocketMQ / RustFS

3.2 模块边界：用「限界上下文」思路分

  • 每个上下文只对自己负责的数据有写权，对外只暴露接口。
  • 依赖方向单向：接入 → 业务 → 能力 → 基础设施；禁止反向调用。
  • Ragent 把「对话」「检索」「入库」「意图」「模型路由」拆成独立包，互不污染。

3.3 以 Ragent 模拟：一次问答的数据流

前端 → 网关鉴权 → 限流排队 → 服务编排(雪花ID) → 加载记忆 → 改写问题 → 意图识别 → 多路检索 → RRF融合 → Rerank → 模型首包探测流式输出 → SSE 推前端。每一环都是一个可独立替换、可独立观测的节点。

四、阶段四：逐功能技术拆解（核心，含优缺点）

下面把 Ragent 的每个功能拆开，讲「用什么技术、为什么、优缺点、备选」。这是本库最值钱的部分。

4.1 对话问答核心链路：SSE 还是 WebSocket？

方案优点缺点适用
SSE（Server-Sent Events）基于 HTTP、天然断线重连、单向推送简单、好过代理只能服务端→客户端单向；二进制弱AI 流式回答（Ragent 选它）
WebSocket全双工、双向实时、可传二进制需自己管心跳/重连、代理/CDN 支持参差协同编辑、聊天室、游戏
普通轮询实现最简单延迟高、空转浪费极简场景、临时方案
  • 取舍：AI 回答是「服务端一直推、客户端只发一次问题」，SSE 最契合；还要支持「中途停止」，用单独的 POST /stop 接口即可，不必为双向而 WebSocket。
Java · Spring Boot SSE（最小可运行）4.1
@GetMapping(value = "/chat", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter chat(@RequestParam String q) {
    SseEmitter em = new SseEmitter(0L);          // 0 = 不限时
    answerService.stream(q)                       // 业务层返回的 Flux<String>
        .subscribe(
            chunk -> em.send(SseEmitter.event().data(chunk)),
            err   -> em.completeWithError(err),
            em::complete);
    return em;                                    // 前端用 EventSource 接收
}

4.2 并发限流：队列式限流 vs 令牌桶

方案优点缺点
令牌桶 / 漏桶（Guava / Redis）实现简单、平滑限平均速率突发时直接拒绝，用户体验差；不保证「先到先服务」
信号量 + 排队（Ragent 队列式）满负载时排队等待而非拒绝，公平且体验好实现复杂（需 Lua 原子出队、僵尸清理、超时状态机）
  • 参数示例：全局并发 50、排队上限 20s、许可租约 600s 兜底防泄漏；被拒回写记忆并推「系统繁忙」。
  • 何时选队列：下游（LLM）是稀缺资源、且希望用户「等一下而非直接失败」；何时选令牌桶：纯接口防刷、不在乎个别请求失败。
Java · 令牌桶 vs 队列式（最小可运行）4.2
// 令牌桶（Guava RateLimiter）：拿不到立即拒绝
RateLimiter rl = RateLimiter.create(50.0);     // 50 许可/秒
if (rl.tryAcquire()) handle(req);
else reject429(req);

// 队列式（Ragent）：满则进带 TTL 的队列等待，而非拒绝
if (semaphore.tryAcquire(20, SECONDS)) {       // 20s 排队上限
    try { handle(req); }
    finally { semaphore.release(); }
} else { reject429(req); }                       // 仍超限才拒绝

4.3 检索增强（RAG）：向量 / 关键词 / 混合，怎么选？

检索方式优点缺点典型用
向量检索（Embedding + 近似近邻）语义匹配强，问法不同也能命中精确值/专名弱；依赖 Embedding 质量口语化、语义相似问题
关键词检索（ES / 倒排）精确匹配、专名/编号准、可解释同义/泛化能力差订单号、术语、法规条文
混合检索（多路并行 + RRF 融合）兼顾语义与精确，召回更全链路更长、要调权重与融合参数生产级知识库（Ragent 选它）
Rerank 精排在召回基础上重排，相关性更高额外一次模型调用、有成本候选多、要保 Top 质量时开启
  • RRF 融合公式：score = Σ weight / (k + rank + 1)；各通道权重可配（vector/keyword/graph/web），融合后截断再送 Rerank。
  • 取舍：MVP 先上向量检索跑通；召回不够再补关键词；质量不稳再加 Rerank——逐级加复杂度。
算法 · RRF 融合（最小可运行）4.3
// 多通道召回按排名倒数求和，再截断送 Rerank
double scoreOf(String docId) {
    double s = 0;
    for (Channel ch : channels) {               // vector / keyword / graph ...
        int rank = ch.rankOf(docId);            // 1-based 排名
        s += ch.weight / (60 + rank);           // k = 60 平滑
    }
    return s;
}
List<Doc> fused = docs.sortBy(this::scoreOf).take(topK);

👉 相关：向量库怎么落地见 5.2 向量库选型。

4.4 意图识别：LLM 分类 vs 传统 ML/NLP

方案优点缺点
LLM 一次性打分（Ragent）零训练、可改 Prompt、多意图一次出有延迟与成本、需设阈值防误判
传统文本分类（BERT 微调）快、便宜、可本地化要标注数据、要训练维护、改意图要重训
关键词/规则路由极快、可控死板、覆盖低、维护地狱
  • 参数：意图阈值 0.35、最多 3 个意图、temperature=0.1/topP=0.3 求稳；结果缓存 7 天减少重复调用。

4.5 会话记忆与上下文压缩

  • 不压缩：实现简单，但长对话爆 token、贵且慢。
  • 滑动窗口（保留最近 N 轮）：简单有效，但会丢早期上下文。
  • 摘要压缩（Ragent）：保留 8 轮原文 + 超 9 轮开始摘要（≤200 字）；优点是不丢全局背景，缺点是异步摘要有延迟、要分布式锁防并发。
  • 取舍：MVP 用滑动窗口；对话长、要连续性的业务再上摘要。Ragent 默认关摘要，按需开。
算法 · 滑动窗口 + 摘要压缩（最小可运行）4.5
List<Turn> recent = history.tail(8);          // 保留最近 8 轮原文
if (history.size() > 9) {
    String summary = cache.getOrLock(userId, () ->  // 分布式锁防并发
        llm.summarize(history.except(recent), 200)); // 超 9 轮开始摘要，≤200 字
    prompt = concat(summary, recent);
} else {
    prompt = concat(recent);                    // 否则直接用原文
}

4.6 模型路由与容错：多模型 / 熔断 / 降级 / 首包探测

机制解决什么要点
多模型路由不同任务用不同模型（快/贵）分 defaultTier / deepThinkingTier 档位
熔断（三态）某模型连续失败不再傻等连续失败 2 次→OPEN 30s→半开放探针
降级主模型挂了切备胎候选有序列表即降级顺序
首包探测流式过程中某个模型不吐字就换按各模型 timeoutMs 探测，ERROR/TIMEOUT 即切下一个
  • 取舍：单模型能跑通就别上全套容错；当依赖外部 LLM API（不稳定）时，熔断+降级是必选项而非可选项。
算法 · 多模型路由 + 熔断 + 首包探测（最小可运行）4.6
for (Model m : candidates) {                  // 候选顺序即降级顺序
    if (breaker.isOpen(m)) continue;           // 熔断中跳过
    try (Probe p = m.stream(prompt, m.timeoutMs)) {
        p.waitFirstToken();                    // 首包探测：超时即切下一个
        return p.pipeToClient();               // 成功则直推前端
    } catch (Timeout | Error e) {
        breaker.fail(m);                        // 连续失败→OPEN 30s
    }
}
return fallbackAnswer();                        // 全部失败→降级回复

4.7 知识库管理与文档入库 Pipeline

  • 四步：解析（PDF/Word/网页）→ 分块（按语义/固定长度）→ Embedding → 写库（文档-分块-向量三级）。
  • 分块策略：固定长度简单但易切断语义；按标题/段落切更连贯但实现复杂。Ragent 用 NodeConfig 连线执行，validatePipeline 校验环防死循环。
  • 入库异步化：大文件走后台任务 + 状态表（pipeline/node/task 三级状态），前端轮询进度。

4.8 认证授权与多租户

方案优点缺点适用
JWT（无状态）不用查库、易横向扩展注销难（需黑名单）、过期固定纯 API、无强制即时注销
Session + Redis可即时注销、可控要存服务端状态要强管控的后台
Sa-Token（Ragent 选）API 简洁、登录/踢人/权限一体引入框架依赖中后台快速落地
  • 多租户：数据隔离三档——独立库（最安全最贵）/ 共享库+tenant_id 行级（最省最易漏）/ 独立 schema（折中）。Ragent 用 UserContextInterceptor 把用户上下文透传，查询统一带租户条件。

4.9 可观测性：Trace / 日志 / 指标 / 审计

  • Trace：一次问答用 TraceId 串起所有节点（run/节点两级），出问题时一眼定位慢在哪。
  • 日志：结构化（JSON）+ 级别分级；敏感信息脱敏。
  • 指标：QPS / 延迟 / 限流拒绝数 / 模型失败率，接 Prometheus + Grafana。
  • 审计：关键写操作留 t_biz_change_log，合规与排错都要。

4.10 异步与消息队列（RocketMQ / Kafka）

中间件优点缺点适用
RocketMQ事务消息、低延迟、Java 生态友好运维略重金融/订单/国内业务（Ragent 选）
Kafka超高吞吐、生态广事务弱、延迟略高日志流、大数据管道
RabbitMQ路由灵活、易上手吞吐中等中小业务、复杂路由
  • 用在哪：文档入库完成通知、记忆摘要触发、异步审计——把「可延迟」的事从主链路摘出去。

4.11 文件与对象存储（S3 兼容）

  • 自建 MinIO / RustFS 还是云 OSS？有合规/成本考量选自建，求省心选云。
  • 抽象 storage.type=oss/s3，业务只调统一接口，换厂商不动代码。

4.12 多级缓存（Redis）

  • 本地缓存（Caffeine）：极快、扛读多场景；缺点是多实例不一致。
  • 分布式缓存（Redis）：实例间共享；缺点是多一跳网络。
  • 典型用法：意图树缓存（TTL 7 天，节点变更主动失效）、限流计数、会话存活标记。
  • 坑：缓存穿透（空值也缓存 / 布隆）、击穿（热点 key 互斥重建）、雪崩（TTL 加随机）。

五、阶段五：数据存储设计

5.1 关系型库：PostgreSQL vs MySQL

维度PostgreSQLMySQL
向量能力原生 PGVector 扩展，一套库搞定关系+向量需外接向量库
复杂查询CTE/窗口函数/JSON 强够用但偏弱
生态/人力略少人多、资料多
  • Ragent 选 PostgreSQL 17 + PGVector：少养一个向量库、事务一致、运维简单。若团队只熟 MySQL 且向量量小，可 MySQL + 外挂 Milvus。

5.2 向量库选型

方案优点缺点
PGVector（Ragent 默认）与关系库同实例、事务一致、运维省超大数据量性能不如专用库
Milvus十亿级向量、高性能、云原生重、独立集群、运维成本高
Elasticsearch关键词+向量一体、检索生态强资源吃、版本坑多
  • 量级决策：百万级向量以内 PGVector 足够；上亿再考虑 Milvus。

5.3 表设计要点（以 Ragent 23 张表为参考）

  • 按域分表：会话域 / 知识库域 / 意图域 / 入库域 / 观测域，互不交叉。
  • 四级知识模型：库 → 文档 → 分块 → 向量，分块与向量可独立扩。
  • 状态表：长任务（入库/调度）必有状态表，前端才能查进度。

六、阶段六：工程化与并发治理

6.1 线程池隔离：别一个大池子打天下

  • 按工作负载特征拆池：IO 密集池大（如检索 4×CPU）、保 LLM 的池小（摘要 1~2 线程防打爆模型）、入口池与限流许可严格对齐。
  • 用 TtlExecutors 包装保证用户上下文 / TraceId 跨线程透传（否则异步后日志全乱）。
  • 拒绝策略：CallerRuns（降速自保）vs AbortPolicy（快速失败），按场景选。

6.2 配置中心与环境管理

  • 本地 / 测试 / 生产三套 application.yaml，敏感信息走环境变量或配置中心（Nacos/Apollo），别提交密码进代码库。
  • 所有阈值（限流/熔断/记忆轮数）配置化，运维可热更不重启。

6.3 幂等与防重

  • 入口按 userId + 请求指纹 幂等（Ragent 的 @IdempotentSubmit），防止用户连点产生重复回答/扣费。
  • 写操作带唯一键 / 乐观锁，防并发重复插入。

七、阶段七：部署与运维

7.1 容器化起步

  • 一键 docker-compose 起中间件（PG+Redis+MQ+对象存储），开发者本地一条命令跑全流程。
  • 应用本身也打镜像，保证「本地能跑=线上能跑」。

7.2 编排与高可用（K8s）

  • 无状态服务（接入/业务）多副本 + HPA 自动扩；有状态（DB）用托管服务。
  • 探针（liveness/readiness）保证流量只进健康实例。

7.3 灰度与回滚

  • 蓝绿 / 金丝雀：新版本先放 5% 流量，指标正常再全量。
  • 每次发布保留上一个镜像，出问题一键回滚。

7.4 监控告警

  • 四件套：日志（ELK/Loki）+ 指标（Prometheus/Grafana）+ Trace（Jaeger/自建）+ 告警（Webhook/钉钉）。
  • 告警要有「阈值 + 静默 + 升级」，否则告警风暴等于没告警。
