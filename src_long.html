第一部分：核心知识点（八股速查）

1. Java 基础

1.1 谈谈 Java 的跨平台原理

Java 源码编译为字节码（.class），由 JVM 解释/编译执行。不同操作系统安装对应 JVM，字节码无需重新编译即可运行，实现「一次编写，到处运行（Write Once, Run Anywhere）」。

1.2 JDK、JRE、JVM 的关系

  • JVM：Java 虚拟机，负责执行字节码。
  • JRE：Java 运行时环境，包含 JVM + 核心类库，用于运行程序。
  • JDK：Java 开发工具包，包含 JRE + 编译器（javac）、调试工具等，用于开发。
  • 关系：JDK ⊃ JRE ⊃ JVM。

1.3 基本数据类型 vs 包装类

基本类型大小默认值包装类
byte8 bit0Byte
short16 bit0Short
int32 bit0Integer
long64 bit0LLong
float32 bit0.0fFloat
double64 bit0.0dDouble

要点：

  • 基本类型存栈/对象内，包装类存堆（引用）。
  • 自动装箱/拆箱是编译期语法糖（Integer a = 1 实际调用 Integer.valueOf(1)）。
  • Integer 缓存 -128 ~ 127，该区间内 == 比较为 true，区间外为 false（new 出来的除外）。

1.4 == 与 equals 的区别

  • ==：比较基本类型的值；比较引用类型的地址。
  • equals：Object 默认等价于 ==，但多数类（如 String、Integer）重写了它来比较内容。
  • 重写 equals 必须重写 hashCode（否则 HashMap 等行为异常）。

1.5 String、StringBuffer、StringBuilder

  • String：不可变（final char[]），每次拼接产生新对象，线程安全。
  • StringBuffer：可变，方法加 synchronized，线程安全，效率低。
  • StringBuilder：可变，非线程安全，效率高（单线程首选）。
  • 字符串拼接建议：少量用 +（编译优化为 StringBuilder）；循环内必须用 StringBuilder。

1.6 String 为什么不可变？好处是什么？

  • 底层 private final char[]（Java 9 后为 byte[] + coder），final 保证引用不变，private 且无修改方法。
  • 好处：字符串常量池可复用、线程安全、适合做 HashMap 的 key、类加载安全。

1.7 重写（Override）与重载（Overload）

  • 重载：同一类中，方法名相同、参数列表不同（类型/个数/顺序），与返回值无关。编译期多态。
  • 重写：子类重写父类方法，方法签名相同，访问修饰符不能更严格，抛出的异常不能更宽泛。运行期多态。

1.8 异常体系

Code
Throwable
 ├── Error（程序无法处理的严重错误，如 OOM、StackOverflow）
 └── Exception
      ├── RuntimeException（非受检，如 NPE、除零、下标越界）
      └── 其他 Exception（受检，如 IOException，必须 try 或 throws）
  • finally 一定执行（除非 System.exit）。try 中有 return，finally 仍先执行；若 finally 也有 return，覆盖前者。

1.9 final、finally、finalize

  • final：修饰类不可继承、方法不可重写、变量不可变（引用不可变，对象内容可变）。
  • finally：异常处理的必定执行块。
  • finalize：Object 的方法，GC 前调用，已废弃（Java 9+ 标记 deprecated），不要用。

1.10 什么是反射？优缺点？

  • 运行时获取类信息并操作对象（Class、Method、Field）。框架（Spring、MyBatis）大量使用。
  • 优点：解耦、动态加载、提高灵活性。
  • 缺点：破坏封装、性能略低、安全受限。

2. 面向对象

2.1 三大特性

  • 封装：隐藏实现细节，暴露接口，提高安全性与可维护性。
  • 继承：子类复用父类代码，单继承（类）/ 多实现（接口）。
  • 多态：同一接口不同实现，父类引用指向子类对象，运行期绑定。

2.2 面向对象 vs 面向过程

  • 面向过程：以函数/步骤为中心，性能略高，适合简单场景。
  • 面向对象：以对象为中心，易扩展、易维护，适合大型系统。

2.3 接口与抽象类的区别

维度抽象类接口
关键字abstractinterface
方法可有具体方法Java 8+ 可有 default/static
变量普通变量默认 public static final
继承单继承多实现

2.4 深拷贝 vs 浅拷贝

  • 浅拷贝：复制引用，原对象与副本共享内部对象。
  • 深拷贝：递归复制所有引用对象，彼此独立。
  • 实现：实现 Cloneable 重写 clone()；或序列化；或手动 new。

3. 集合框架

3.1 整体结构

Code
Collection
 ├── List（有序、可重复）：ArrayList、LinkedList、Vector、Stack
 ├── Set（不可重复）：HashSet、LinkedHashSet、TreeSet
 └── Queue：ArrayDeque、PriorityQueue、BlockingQueue
Map（键值对）：HashMap、LinkedHashMap、TreeMap、Hashtable、ConcurrentHashMap

3.2 ArrayList vs LinkedList

  • ArrayList：基于动态数组，随机访问 O(1)，插入删除（非尾部）需移动元素 O(n)，扩容 1.5 倍。
  • LinkedList：基于双向链表，插入删除 O(1)（已知节点），随机访问 O(n)，额外内存开销（前后指针）。

3.3 HashMap 原理（重点）

  • JDK 1.7：数组 + 链表，头插法（多线程易成环）。
  • JDK 1.8：数组 + 链表 + 红黑树。
  • 默认容量 16，负载因子 0.75，阈值 = 容量 × 负载因子。
  • 链表长度 ≥ 8 且数组容量 ≥ 64 时转红黑树；树节点 ≤ 6 退化为链表。
  • 计算下标：(n - 1) & hash，hash 经 hashCode ^ (h >>> 16) 扰动。
  • 扩容 2 倍，重新分布（低位/高位链表）。
  • 线程不安全：并发 put 可能导致数据覆盖、死循环（1.7）。并发场景用 ConcurrentHashMap。

3.4 ConcurrentHashMap

  • JDK 1.7：Segment 分段锁（ReentrantLock），默认 16 段。
  • JDK 1.8：取消 Segment，使用 Node + CAS + synchronized（锁链表头节点），粒度更细，效率更高。

3.5 HashSet 如何保证不重复

  • 基于 HashMap 实现，元素作为 key，value 为固定 Object。靠 hashCode() + equals() 判断重复。

3.6 fail-fast 与 fail-safe

  • fail-fast：遍历时若集合被修改（非迭代器自身），抛出 ConcurrentModificationException。ArrayList 等默认。
  • fail-safe：基于副本遍历，不抛异常，但读到的是旧数据。CopyOnWriteArrayList、ConcurrentHashMap 迭代器。

4. 并发与多线程（JUC）

4.1 进程与线程

  • 进程：资源分配的最小单位，独立内存空间。
  • 线程：CPU 调度的最小单位，同进程内线程共享内存。

4.2 创建线程的方式

  1. 继承 Thread 重写 run。
  2. 实现 Runnable（无返回值）。
  3. 实现 Callable（有返回值，配合 FutureTask）。
  4. 线程池 ExecutorService。

4.3 线程的生命周期

新建 → 就绪 → 运行 → 阻塞（wait/sleep/IO/锁）→ 死亡。

  • sleep：不释放锁，Thread 静态方法。
  • wait：释放锁，Object 方法，需配合 notify/notifyAll，在 synchronized 内调用。

4.4 synchronized 关键字

  • 修饰方法/代码块，保证原子性、可见性、有序性。
  • 底层：对象头 Mark Word + Monitor（管程）。JDK 1.6 后引入锁升级：无锁 → 偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁（操作系统互斥）。

4.5 volatile

  • 保证可见性（写立即刷主存，读从主存取）与有序性（禁止指令重排）。
  • 不保证原子性（如 i++ 仍是三步操作）。
  • 经典用法：状态标志位、双重检查单例。

4.6 synchronized vs volatile

维度synchronizedvolatile
原子性保证不保证
可见性保证保证
有序性保证（锁）保证（屏障）
阻塞会不会

4.7 锁分类

  • 公平/非公平锁：是否按申请顺序获取（ReentrantLock 可设置，默认非公平）。
  • 可重入锁：同一线程可重复获取（synchronized、ReentrantLock）。
  • 悲观锁/乐观锁：synchronized 是悲观；CAS 是乐观。
  • 自旋锁：失败后忙等一段时间，避免线程切换开销。
  • 读写锁：ReadWriteLock，读共享、写独占。

4.8 CAS 是什么？有什么问题？

  • Compare And Swap：比较并交换，无锁原子操作（CPU 指令级）。
  • 问题：ABA 问题（加版本号/时间戳解决，如 AtomicStampedReference）、自旋开销大、只能保证一个变量原子性。

4.9 线程池

  • 核心参数（ThreadPoolExecutor）：
  • corePoolSize：核心线程数
  • maximumPoolSize：最大线程数
  • keepAliveTime：空闲线程存活时间
  • workQueue：任务队列（ArrayBlockingQueue、LinkedBlockingQueue、SynchronousQueue）
  • threadFactory：线程工厂
  • handler：拒绝策略
  • 执行流程：核心线程满 → 入队列 → 队列满 → 开非核心线程 → 达最大线程数 → 触发拒绝策略。
  • 拒绝策略：AbortPolicy（抛异常，默认）、CallerRunsPolicy（调用者线程执行）、DiscardPolicy（丢弃）、DiscardOldestPolicy（丢弃最老）。
  • Executors 的隐患：FixedThreadPool / SingleThreadPool 用无界队列易 OOM；CachedThreadPool 最大线程数无界易 OOM。建议手动 new ThreadPoolExecutor。

4.10 ThreadLocal

  • 线程本地变量，每个线程有独立副本，避免共享。
  • 原理：Thread 内有 ThreadLocalMap，key 为 ThreadLocal 弱引用。
  • 内存泄漏：key 弱引用被 GC 后 value 仍是强引用，需手动 remove()。

5. JVM

5.1 运行时数据区

  • 线程私有：程序计数器、虚拟机栈、本地方法栈。
  • 线程共享：堆、方法区（元空间 Metaspace，JDK 8 取代永久代）。

5.2 堆内存划分

  • 新生代（Eden + 两个 Survivor S0/S1）、老年代。
  • 对象优先在 Eden 分配，Minor GC 后存活的进入 Survivor，年龄达阈值（默认 15）进入老年代。

5.3 垃圾回收算法

  • 标记-清除：简单但有碎片。
  • 标记-整理：无碎片，移动对象开销大（老年代）。
  • 复制算法：无碎片，浪费一半空间（新生代）。
  • 分代收集：新生代用复制，老年代用标记-整理/清除。

5.4 垃圾收集器

  • Serial / Serial Old：单线程，简单。
  • ParNew：Serial 多线程版，配合 CMS。
  • Parallel Scavenge / Parallel Old：吞吐量优先。
  • CMS：并发标记清除，低停顿，但碎片、CPU 敏感、Concurrent Mode Failure。
  • G1：分 Region，可预测停顿，兼顾吞吐与延迟（JDK 9+ 默认）。
  • ZGC / Shenandoah：超低停顿（毫秒级）。

5.5 如何判断对象可回收？

  • 引用计数：简单但有循环引用问题。
  • 可达性分析：GC Roots（栈引用、静态变量、常量、JNI）不可达即为可回收。至少两次标记（finalize 自救一次）。

5.6 双亲委派模型

  • 类加载器层级：Bootstrap → Extension → Application → 自定义。
  • 加载时先委派父加载器，父无法加载才自己加载。
  • 好处：避免重复加载、防止核心类被篡改。
  • 破坏场景：SPI（JDBC）、热部署、Tomcat WebAppClassLoader。

5.7 常见 OOM / 调优参数

  • -Xms / -Xmx：堆初始/最大。
  • -Xmn：新生代大小。
  • -XX:MetaspaceSize：元空间。
  • 排查工具：jps、jstat、jmap、jstack、jvisualvm、Arthas。

1. 集合：购物车与商品去重

业务背景 用户加购同一商品多次，前端可能重复提交；购物车需要展示「不重复的商品 + 各自数量」。

用到的知识点

  • HashMap：以 skuId 为 key，数量 为 value，天然去重。
  • LinkedHashMap：需要保持加购顺序时选用。
  • HashSet：批量校验「已存在的 skuId 集合」。
  • 不可变对象做 key 时必须正确重写 equals + hashCode（SKU 用 id 即可）。

Map<Long, Integer> cart = new LinkedHashMap<>();
for (SkuItem item : items) {
    cart.merge(item.getSkuId(), item.getCount(), Integer::sum); // 合并数量
}

2. HashMap / ConcurrentHashMap：本地缓存与热点计数

业务背景 商品详情页高频访问，DB 扛不住，加一层本地缓存；同时实时统计「商品被浏览次数」做热门榜单。

用到的知识点

  • ConcurrentHashMap 做本地缓存（Caffeine 底层也是它 + 近似 LRU）。
  • 并发计数用 ConcurrentHashMap + LongAdder（分段 CAS，比 AtomicLong 高并发更优）。
  • 缓存与 Redis 的层级关系（本地缓存 → Redis → DB）。

关键实现思路

Code
private final Map<Long, ProductVO> cache = new ConcurrentHashMap<>();
private final Map<Long, LongAdder> viewCount = new ConcurrentHashMap<>();

public ProductVO getProduct(Long id) {
    return cache.computeIfAbsent(id, this::loadFromDb);
}
public void incrView(Long id) {
    viewCount.computeIfAbsent(id, k -> new LongAdder()).increment();
}

面试追问

  • 本地缓存和 Redis 缓存各自优缺点？（本地最快但各节点不一致，Redis 集中但有网络开销）
  • 为什么热点计数用 LongAdder 而不是 AtomicLong？（高并发下 AtomicLong CAS 竞争激烈，LongAdder 分 cell 分散竞争）
  • 缓存一致性怎么保证？（更新 DB 后删本地缓存 + 发广播/消息让其他节点失效）

3. synchronized / 锁：秒杀库存扣减

业务背景 秒杀活动，1 万人在同一秒抢 100 件商品，必须保证「不超卖、不超扣」。

用到的知识点

  • 单机：synchronized / ReentrantLock 保护库存扣减临界区。
  • 分布式：必须上分布式锁（Redis SETNX / Redisson）或数据库乐观锁（UPDATE ... WHERE stock > 0）。
  • CAS / 原子类在单体场景的替代。

关键实现思路（单体 + 数据库乐观锁兜底）

Code
// 先 Redis 预扣（Lua 原子脚本保证原子性）
Long remain = redisTemplate.execute(decrScript, List.of(stockKey));
if (remain < 0) { redisTemplate.incr(stockKey); return "售罄"; }
// 异步落库，数据库再 WHERE stock>0 兜底防超卖
int rows = itemMapper.decrStock(itemId);
if (rows == 0) { redisTemplate.incr(stockKey); return "售罄"; }

面试追问

  • 只靠 synchronized 为什么扛不住秒杀？（单机锁，集群多实例各自扣自己的，照样超卖）
  • 为什么用 Lua 脚本做 Redis 预扣？（保证「判断+扣减」原子，避免 check-then-act 竞态）
  • 库存扣成负数怎么防？（Lua 返回后判断 + 数据库 WHERE 条件双重保险）

4. volatile：系统开关与单例配置中心

业务背景

  • 运营要临时关闭某个营销活动（如「双11预热」），不想发版就能即时生效。
  • 配置中心（如 Nacos/Apollo）推送配置后，应用要立刻读到新值。

用到的知识点

  • volatile 保证可见性：一个线程改了，其他线程立刻可见。
  • 典型用法：布尔开关 private volatile boolean activityOn;。
  • 不能保证原子性：开关只是赋值 OK，但 i++ 类的计数不行。

关键实现思路

Code
@Component
public class ActivitySwitch {
    private volatile boolean open = false;
    @Value("${activity.open:false}") public void setOpen(boolean v){ this.open = v; }
    public boolean isOpen(){ return open; }
}

面试追问

  • 为什么开关用 volatile 而不是 synchronized？（开关只是写读布尔值，volatile 无锁更轻量）
  • 配置中心推送后为什么能立刻生效？（监听器 set 新值 + volatile 保证可见）
  • 单例 DCL 为什么必须 volatile？（防止指令重排导致返回半初始化对象）

5. 线程池：异步通知与批量任务

用到的知识点

  • 自定义 ThreadPoolExecutor，不用 Executors（防 OOM）。
  • 核心/最大线程数、队列、拒绝策略选型。

关键实现思路

6. ThreadLocal：用户上下文与链路追踪

业务背景 一次请求里多处需要「当前登录用户」「TraceId」，不想每层方法都传参；同时要避免用户信息串号。

用到的知识点

  • ThreadLocal 存请求级上下文（UserContext、MDC TraceId）。
  • 必须 remove()，否则线程池复用导致串数据（内存泄漏 + 串号）。
  • Spring MVC 拦截器 preHandle 设值、afterCompletion 清理。

关键实现思路

Code
public class UserContext {
    private static final ThreadLocal<User> TL = new ThreadLocal<>();
    public static void set(User u){ TL.set(u); }
    public static User get(){ return TL.get(); }
    public static void clear(){ TL.remove(); } // 关键！
}

面试追问

  • 为什么线程池里不 remove 会串号？（线程复用，下次请求读到上次的 user）
  • ThreadLocal 内存泄漏原因？（key 弱引用被 GC，value 强引用残留，remove 清理）
  • TraceId 怎么跨线程传递？（InheritableThreadLocal 或 TransmittableThreadLocal 解决线程池透传）

7. JVM / GC：大促接口超时排查

业务背景 大促期间，订单接口每隔几分钟就出现一波 1~2 秒超时，平时正常。

用到的知识点

  • GC 日志分析（-Xlog:gc* / -XX:+PrintGCDetails）。
  • 频繁 Full GC 导致 Stop-The-World，请求被「冻结」。
  • 排查链路：监控告警 → 看 GC 频次/耗时 → 堆 dump 分析大对象 → 定位内存泄漏/缓存无上限。

关键实现思路

Code
# 抓现场
jstat -gcutil <pid> 1000      # 看各区占用与 GC 次数
jmap -dump:live,format=b,file=heap.hprof <pid>  # 堆转储
# 用 MAT / VisualVM / Arthas 分析：谁占了多少
  • 常见根因：本地缓存 HashMap 无上限、ThreadLocal 未 remove、大对象（一次性读全表）。

面试追问

  • Full GC 和 Young GC 区别？（回收范围、触发条件、停顿时长）
  • 为什么大促才出问题平时没事？（流量翻倍触发缓存膨胀 / 对象分配速率陡增）
  • 怎么预防？（缓存加容量上限+过期、压测、监控 GC 告警）

9. 设计模式：支付与促销策略

用到的知识点

  • 工厂模式：根据渠道创建对应支付 SDK 实例。
  • 观察者模式：订单支付成功后，发消息通知积分、物流、风控（解耦）。
  • 责任链模式：风控校验多道关卡串行。

关键实现思路

Code
Map<PayType, PayStrategy> strategies = ...; // Spring 自动注入所有实现
public String pay(PayType type, Order o){
    return strategies.get(type).pay(o); // 新增支付方式只加实现类
}

  • 观察者模式在这里解决了什么？（支付核心与积分/物流解耦，互不影响）

10. MySQL 索引：订单查询慢 SQL

业务背景 运营后台「查某用户最近 3 个月订单」，未加索引时全表扫描，接口 5 秒。

用到的知识点

  • 联合索引 (user_id, create_time) 命中最左前缀，既能按用户又能按时间范围。
  • 避免索引失效：不要在字段上套函数（WHERE DATE(create_time)=... 会失效）、避免 %前缀 模糊。
  • 覆盖索引避免回表（SELECT 只取索引列）。

关键实现思路

Code
-- 建联合索引
ALTER TABLE orders ADD INDEX idx_user_time (user_id, create_time);
-- 查询（走索引，范围在右列）
SELECT id, amount FROM orders
WHERE user_id = 123 AND create_time >= '2026-05-01'
ORDER BY create_time DESC LIMIT 20;

面试追问

  • 为什么联合索引顺序是 user_id 在前？（高频等值查询在前，范围在后，否则索引失效）
  • 怎么验证走没走索引？（EXPLAIN 看 type/key/rows/extra）
  • 回表是什么？（二级索引存主键，需再用主键查整行；覆盖索引可免）

11. 事务：下单扣库存与转账

业务背景 下单要「扣库存 + 创建订单 + 扣余额」要么全成功要么全失败；银行转账 A 减 B 加必须原子。

用到的知识点

  • @Transactional 声明式事务（AOP 代理）。
  • 事务隔离级别解决脏读/不可重复读/幻读。
  • 事务失效场景：同类自调用、非 public、异常被吞。
  • 跨服务用分布式事务（Seata TCC / 消息最终一致性）。

关键实现思路

Code
@Transactional(rollbackFor = Exception.class, isolation = Isolation.REPEATABLE_READ)
public void createOrder(OrderCmd cmd){
    stockMapper.decr(cmd.getSkuId(), cmd.getCount()); // 扣库存
    orderMapper.insert(cmd.toOrder());                // 建订单
    accountMapper.decr(cmd.getUserId(), cmd.getAmount()); // 扣款
    // 任一异常整体回滚
}

面试追问

  • 为什么自调用事务不生效？（Spring 走代理，内部调用没过代理，没织入事务）
  • 扣库存和扣款不在同一个库怎么办？（跨库 → 分布式事务 / 最终一致 + 补偿）
  • 大事务有什么危害？（锁久、连接占用、回滚慢，应拆解 + 异步）

12. Redis：缓存与分布式锁

业务背景

  • 商品详情缓存，扛读流量。
  • 秒杀 / 定时任务防止集群多节点重复执行。

用到的知识点

  • 缓存三大坑：穿透（布隆过滤器）、击穿（互斥锁/逻辑过期）、雪崩（过期时间加随机）。
  • 分布式锁：SET key value NX EX 原子加锁 + Lua 释放（防误删）+ Redisson 看门狗自动续期。
  • 缓存与 DB 一致性：先更新 DB 再删缓存（Cache-Aside）。

关键实现思路

Code
// 加锁（Redisson 简化写法）
RLock lock = redissonClient.getLock("task:sync");
if (lock.tryLock(0, 30, TimeUnit.SECONDS)) {
    try { doSync(); } finally { lock.unlock(); }
}
// 缓存读取
Product p = redis.get(key);
if (p == null) {
    p = db.load(id);
    redis.setex(key, 300 + RandomUtil.randomInt(60), p); // 过期加随机防雪崩
}

面试追问

  • 为什么释放锁要用 Lua？（判断+删除必须原子，否则可能删掉别人的锁）
  • 缓存和数据库不一致怎么解决？（更新 DB 后删缓存；延迟双删兜底）
  • Redisson 看门狗做什么？（锁快过期时自动续期，防止业务没跑完锁没了）

13. Spring：循环依赖 / AOP / 事务失效

业务背景

  • 支付服务 A 依赖风控服务 B，B 又依赖 A（循环依赖）。
  • 统一记录接口耗时、统一登录校验。

用到的知识点

  • 循环依赖：Spring 用三级缓存解决（singletonObjects / earlySingletonObjects / singletonFactories），允许「提前暴露半成品 bean」注入。
  • AOP：用动态代理织入日志、鉴权、事务（JDK 代理基于接口，CGLIB 基于继承）。
  • 事务失效：自调用、异常被 catch、非 public、数据库引擎不支持。

关键实现思路

Code
@Aspect @Component
public class LogAspect {
    @Around("execution(* com.x..service..*(..))")
    public Object log(ProceedingJoinPoint pjp) throws Throwable {
        long s = System.currentTimeMillis();
        try { return pjp.proceed(); }
        finally { log.info("{} 耗时{}ms", pjp.getSignature(), System.currentTimeMillis()-s); }
    }
}

面试追问

  • 三级缓存具体怎么破循环依赖？（一二三级分别存成品/早期引用/工厂，提前曝光解决）
  • 构造器注入的循环依赖能解决吗？（不能，需 @Lazy 或改设计）
  • 为什么 CGLIB 能代理类而 JDK 只能代理接口？（CGLIB 生成子类，JDK 用 InvocationHandler）

15. 消息队列：下单异步解耦

orderTx.execute(() -> {

1. 微服务与 Spring Cloud 生态

1.1 微服务核心组件

  • 注册中心：Eureka（AP，CAP 中保证可用）、Nacos（AP/CP 可切换，集注册+配置）、Consul、ZooKeeper（CP）。
  • 配置中心：Nacos、Apollo（携程）、Spring Cloud Config。
  • 网关：Spring Cloud Gateway（WebFlux、断言+过滤器）、Zuul（1.x 阻塞，已淘汰）。
  • 负载均衡：Spring Cloud LoadBalancer / Ribbon（轮询、随机、加权、一致性哈希）。
  • 熔断降级限流：Sentinel（滑动窗口、熔断规则、热点限流）、Hystrix（已停更）。
  • 链路追踪：Sleuth + Zipkin / SkyWalking（无侵入字节码插桩）。

1.2 服务注册与发现原理

  • 服务启动时向注册中心注册元数据（IP、端口、服务名）。
  • 消费者拉取/订阅服务列表（推拉结合 + 心跳续约）。
  • 注册中心通过心跳判断实例存活，剔除失效节点。
  • 客户端缓存服务列表，注册中心宕机仍可短期调用（最终一致）。

1.3 网关（Gateway）作用

  • 路由：根据断言（Path、Header、Cookie）转发到对应服务。
  • 鉴权：统一 JWT / OAuth2 校验，拦截非法请求。
  • 限流：基于令牌桶 / 计数器，保护后端。
  • 灰度 / 熔断：按版本路由、集成 Sentinel 熔断。

1.4 负载均衡：Ribbon vs Nginx

  • Ribbon：客户端负载均衡（进程内，知道所有实例，选一个再调）。
  • Nginx：服务端负载均衡（独立节点，集中转发）。
  • 区别：Ribbon 减少一跳、支持更细策略；Nginx 与语言无关、可做 L4/L7。

1.5 熔断、降级、限流

  • 熔断：错误率/慢调用超阈值，打开熔断器，一段时间后半开探测（Sentinel 三种状态）。
  • 降级：流量激增或依赖故障时，返回兜底（默认值 / 缓存 / 静态页）。
  • 限流算法：
  • 计数器（固定窗口，有临界突刺问题）。
  • 滑动窗口（细分时间片，更平滑）。
  • 漏桶（恒定速率流出，整形）。
  • 令牌桶（恒定速率发令牌，允许突发，最常用）。

面试追问

  • Eureka 与 Nacos 在 CAP 上的取舍？（Eureka 选 AP 保证可用；Nacos 可切 CP 保证强一致）
  • Sentinel 和 Hystrix 区别？（Hystrix 线程池隔离资源占用大；Sentinel 信号量 + 滑动窗口，更轻量）
  • 网关为什么要做限流而不是只靠服务自身？（边缘拦截，避免无效流量打到内网）

2. 消息队列（MQ）

2.1 为什么用 MQ

  • 解耦：生产者不关心谁消费（如下单后发券、积分、通知各自订阅）。
  • 异步：非核心链路异步化，主流程快返回。
  • 削峰：突发流量先入队，消费者按能力平稳处理（如秒杀）。

2.2 Kafka / RabbitMQ / RocketMQ 对比

维度KafkaRabbitMQRocketMQ
定位高吞吐日志/流低延迟、路由灵活业务消息、事务
吞吐量极高中高
延迟低（批）极低低
事务消息无（0.11+ 有幂等）无有（半事务）
顺序消息分区有序队列有序队列有序
典型场景日志、大数据企业总线、任务电商交易

2.3 消息可靠性（不丢）

  • 生产端：confirm 机制（RabbitMQ）、acks=all + 重试（Kafka）。
  • 服务端：刷盘（同步/异步）+ 主从复制。
  • 消费端：先处理业务再手动 ack，处理失败不 ack（重回队列 / 死信）。

2.4 重复消费与幂等

  • 原因：网络重试、rebalance、消费超时。
  • 幂等方案：业务唯一键（订单号）去重表、Redis SETNX、状态机（已处理则跳过）、数据库唯一索引。

2.5 消息积压处理

  • 临时扩容消费者实例 + 提升消费并发。
  • 如果消费慢：开启多线程消费 / 批量消费。
  • 极端：新建临时 Topic，把积压消息转发后快速消费。

2.6 顺序消息

  • Kafka：同一业务 key 发到同一 partition，单 partition 内有序。
  • RocketMQ：同一 MessageQueue 有序，用顺序发送 + 加锁消费。

面试追问

  • 如何保证消息不丢失？（三端确认：生产 confirm + 服务端持久化 + 消费手动 ack）
  • RocketMQ 事务消息原理？（Half Message → 执行本地事务 → Commit/Rollback，回查保证最终一致）
  • Kafka 为什么快？（顺序写磁盘、零拷贝 sendfile、批量压缩、页缓存）

3. 分布式事务

3.1 2PC / 3PC

  • 2PC（两阶段提交）：准备阶段（各参与者锁资源投票）+ 提交阶段（协调者统一提交/回滚）。缺点：同步阻塞、单点、数据不一致（协调者宕机）。
  • 3PC：引入超时与预询问，降低阻塞，但网络分区仍可能不一致，工业界少用。

3.2 TCC（Try-Confirm-Cancel）

  • Try：预留资源（如冻结库存）。
  • Confirm：真正提交（幂等）。
  • Cancel：释放预留（幂等）。
  • 优点：无长事务锁，性能好；缺点：业务侵入强，需手写三阶段。

3.3 消息最终一致性（常用）

  • 本地消息表：业务与消息同库事务，后台任务投递到 MQ，消费者幂等处理。
  • 事务消息（RocketMQ）：Half Message + 本地事务 + 回查，保证「本地成功必发消息」。
  • 特点：最终一致、性能好、容忍短暂不一致。

3.4 Seata

  • AT 模式：自动生成回滚日志（undo_log），两阶段：一阶段提交本地事务+写undo，二阶段异步清理或回滚（无侵入，最常用）。
  • TCC / SAGA / XA 模式按需选择。

3.5 最大努力通知

  • 多次重试通知 + 对账，适用于跨系统（如支付结果通知），不保证强一致，但尽力送达。

面试追问

  • 你们项目用哪种分布式事务？为什么？（电商常用 消息最终一致 / Seata AT，避免 2PC 长锁）
  • TCC 的空回滚 / 防悬挂是什么？（Try 未收到但收到 Cancel → 记录空回滚；防悬挂：Cancel 先于 Try 到达要拒绝）
  • Seata AT 为什么无侵入？（代理数据源，自动解析 SQL 生成前后镜像）

4. 分布式锁与缓存一致性

4.1 分布式锁方案

  • Redis 实现：SET key value NX EX 原子加锁；Lua 脚本释放（防误删）；Redisson 看门狗自动续期。
  • 优点：高性能；缺点：主从切换可能丢锁（RedLock 争议大）。
  • ZooKeeper 实现：临时有序节点 + 最小节点获锁 + watch 下一节点。
  • 优点：强一致、锁一定不丢；缺点：性能较低、依赖 ZK 集群。
  • 数据库实现：唯一索引 / SELECT ... FOR UPDATE。
  • 优点：简单；缺点：性能差、连接占用。

4.2 缓存与 DB 一致性

  • Cache-Aside（旁路）：读时回填，写时「先更新 DB 再删缓存」。
  • 延迟双删：更新 DB → 删缓存 → 延迟再删一次（防更新期间旧值回填）。
  • binlog 订阅（Canal）：监听 binlog 异步删/更新缓存，解耦业务。
  • 取舍：强一致几乎不可能，追求「最终一致 + 缩短不一致窗口」。

面试追问

  • Redis 锁和 ZK 锁怎么选？（高并发选 Redis；强一致选 ZK）
  • 为什么「先更新 DB 再删缓存」仍可能不一致？（删缓存后、DB 提交前读请求回填旧值 → 延迟双删/订阅 binlog 兜底）
  • Redisson 看门狗原理？（加锁后定时续期，业务完成才释放，防止锁提前过期）

5. 分布式 ID 与分库分表

5.1 分布式 ID 方案

  • UUID：简单无序，作为 DB 主键导致索引碎片化，不推荐。
  • 雪花算法（Snowflake）：时间戳+机器ID+序列号，趋势递增、高性能；依赖时钟（时钟回拨问题）。
  • 号段模式（Leaf-segment）：DB 批量取号段，内存发号，性能好。
  • Leaf-snowflake：解决时钟回拨的雪花改进。
  • 要求：全局唯一、趋势递增（利 B+ 树）、高可用、高性能。

5.2 分库分表

  • 垂直分库：按业务（订单库、用户库）拆分，解耦。
  • 水平分表：单表数据过大，按 分片键（用户ID、订单ID）哈希/范围/时间分片。
  • 中间件：ShardingSphere（JDBC 层 / Proxy）。
  • 带来的问题：
  • 分布式事务（跨库）。
  • 跨分片查询 / 分页 / 排序困难（需归并）。
  • 分片键选择不慎导致数据倾斜。
  • 扩容需迁移数据（一致性哈希可缓解）。

面试追问

  • 分片键怎么选？（高频查询字段、区分度高、避免热点，如订单表用 user_id 或 order_id）
  • 雪花算法时钟回拨怎么办？（等待、记录上次时间、或切换机器位）
  • 分库分表后怎么做跨片分页？（各分片查 TopN 后在应用层归并排序）

一、项目定位与技术栈

1.1 它是什么

Ragent 是一个面向 Agentic RAG 演进的企业级 RAG 平台，核心能力：

  • 多路检索：多渠道并行检索，去重重排兼顾精准与召回。
  • 意图识别：树形多级分类，置信度不足主动引导澄清；节点区分「知识库 / 系统应答 / 工具调用」三类。
  • 模型引擎：模型调度、首包探测、健康检查、自动降级，模型故障不影响服务。
  • MCP 集成：非知识类意图自动提参调用业务工具，检索与工具无缝融合。
它解决的不是「调个 API 就叫 RAG」，而是企业落地 RAG 真实会踩的坑：文档解析、分块策略、召回率、多路融合、幻觉控制、限流熔断、多租户隔离、可观测性。

二、架构分层思想

2.1 三层职责链路

Code
framework  →  infra-ai  →  bootstrap
(横切能力)    (屏蔽供应商)   (业务逻辑)
  • framework：提供与业务无关的通用能力（异常、ID、幂等、上下文透传、SSE）。换业务逻辑不动它。
  • infra-ai：把不同模型供应商的差异收敛到统一接口后面。换模型供应商不碰业务代码。
  • bootstrap：专注业务编排（RAG 流水线、意图、知识库、入库、权限）。

2.2 为什么这么分

分层不是为了炫技，而是解决实际问题：换模型供应商不用改业务代码，换业务逻辑不用动基础设施。infra-ai 里实现 ChatClient 接口即可参与路由，bootstrap 完全无感知。

三、核心业务流程链路：一次问答的全过程 ★重点

3.1 总览（流水线阶段编排）

入口：RAGChatController → RAGChatServiceImpl.streamChat()，主流程由 StreamChatPipeline（rag/service/pipeline/StreamChatPipeline.java）按阶段串联，采用「私有阶段方法 + boolean 短路返回」的轻量编排：

Code
streamChat()
 ├─ ChatQueueLimiter.enqueue()          // 队列式分布式限流
 ├─ StreamChatTraceRunner.run()         // 全链路 Trace 包裹
 └─ StreamChatPipeline.execute(ctx)     // 流水线编排
     ├─ 1. loadMemory(ctx)              // 会话记忆加载
     ├─ 2. rewriteQuery(ctx)            // 问题改写 + 子问题拆分
     ├─ 3. resolveIntents(ctx)          // 意图识别
     ├─ 4. handleGuidance(ctx)          // 歧义引导（置信度不足追问）
     ├─ 5. handleSystemOnly(ctx)        // 纯 SYSTEM 意图：直连 LLM 回复
     ├─ 6. retrieve(ctx)                // 多路检索
     └─ 7. streamRagResponse(ctx)       // 组装 Prompt + 流式输出

3.2 阶段 1：会话记忆加载

ConversationMemoryService.loadAndAppend 加载历史消息。难点不是「存」，而是记忆压缩：20 轮对话全塞给模型 Token 成本扛不住；只带最近几轮又可能丢关键信息。Ragent 用「滑动窗口 + 自动摘要压缩 + TTL 过期」平衡，避免长对话 OOM / Token 爆炸。

3.3 阶段 2：问题改写与子问题拆分

QueryRewriteService.rewriteWithSplit（及 MultiQuestionRewriteService）把用户口语 / 多轮上下文重写为规范子问题：

  • 用户输入「报销咋整」→ 改写为规范查询；
  • 多轮里说「怎么申请」→ 补上下文，否则系统不知道在问啥；
  • 复杂问题拆分为多个子问题分别检索，再融合。
  • 另有 QueryTermMappingService 做同义词 / 术语映射（如「墨盒」↔「墨盒更换」），提升召回。

3.4 阶段 3：意图识别（树形多级）

  • 意图节点 IntentNode：id / parentId / children / level / description / examples / kind，kind 分三类：
  • KB：走知识库检索；
  • SYSTEM：系统应答（直连 LLM，不走检索）；
  • MCP：调用业务工具。
  • 分类器 DefaultIntentClassifier：一次性把全部叶子节点喂给 LLM 打分（temperature=0.1），返回 List<NodeScore>，结果缓存于 Redis（IntentTreeCacheManager）。
  • 解析器 IntentResolver.resolve：按子问题并发分类，过滤 score >= INTENT_MIN_SCORE、上限 MAX_INTENT_COUNT，按 KB / MCP 拆成 IntentGroup。
  • 新增意图节点只需建库，IntentNodeRegistry 自动注册。

3.5 阶段 4：歧义引导

IntentGuidanceService + AmbiguityLLMChecker：当置信度不足时返回澄清提示，让用户补充信息，不直接检索。这是「RAG 常见误区」里强调的工程细节——走错路答案必错。

3.6 阶段 5：多路检索 ★

引擎 MultiChannelRetrievalEngine.retrieveKnowledgeChannels：

  • 检索通道接口 SearchChannel，实现类：
  • VectorSearchChannel（向量，内部按意图置信度二选一：命中库 IntentParallelRetriever / 全库 CollectionParallelRetriever）
  • KeywordSearchChannel（ES 关键词，精确匹配订单号等向量弱项）
  • WebSearchChannel（联网检索）
  • GraphSearchChannel（知识图谱，接 LightRAG）
  • 所有通道通过 CompletableFuture + ragRetrievalExecutor 线程池并行执行。
  • 后处理责任链（接口 SearchResultPostProcessor，按 getOrder() 排序）：
  • DeduplicationPostProcessor（去重）
  • FusionPostProcessor（多通道融合，RRF 倒数排名融合）
  • RerankPostProcessor（精排，调 RerankClient）
  • MetadataEnrichmentPostProcessor（元数据富化，补文档标题等）
纯向量检索对精确匹配很弱（用户问订单号找不到），所以必须混合检索 + 重排序。

3.7 阶段 6：Prompt 组装与流式输出

streamRagResponse 把检索到的上下文 + 会话记忆 + 系统提示组装成 Prompt，通过 SseEmitterSender（framework 提供的线程安全 SSE 封装）实时推送。RoutingLLMService 流式调用时用 ProbeStreamBridge + LlmFirstPacketProbe 做首包探测——首个模型首包超时即切换下一个，用户无感知。

3.8 一张图看懂调用链（文字时序）

Code
用户 → Controller.streamChat
     → ChatQueueLimiter 入队（Redis ZSET + Lua 原子判队头）
     → StreamChatTraceRunner（AOP 全链路 Trace 开始）
     → Pipeline:
        记忆 ← MySQL
        改写 ← LLM
        意图 ← LLM（Redis 缓存意图树）

四、知识库入库链路（Ingestion Pipeline）

文档从上传到可检索，经过一条基于节点编排的 Pipeline：

4.3 切片策略与写入

五、模型路由与故障转移

全部在 infra-ai/.../model/ 与 infra/chat/：

  • 模型选择器 ModelSelector：chat 组走档位（Tier）机制（defaultTier / deepThinkingTier，深度思考路由到支持 thinking 的模型）；embedding / rerank / vlm 走 defaultModel + priority 排序。
  • 三态断路器 ModelHealthStore：CLOSED → OPEN → HALF_OPEN，consecutiveFailures >= failureThreshold 自动熔断，冷却期后放行探测，成功恢复失败继续熔断。
  • 路由执行器 ModelRoutingExecutor.executeWithFallback：遍历候选，调用前 healthStore.allowCall，失败 markFailure 切下一个，全失败抛 RemoteException。
  • 首包探测 RoutingLLMService + LlmFirstPacketProbe：流式首个模型首包超时 / 无内容即 markFailure 并切换下一个，业务层无感知。

十一、生产级工程特性

11.1 队列式分布式限流

ChatQueueLimiter：Redis 信号 + 有序集合（ZSET）+ Pub/Sub 通知。请求先入 ZSET 排队，通过 Lua 脚本原子判断是否在队头窗口内再出队，信号量控制最大并发数并支持许可自动过期（防死锁）。跨实例通过 Pub/Sub 广播唤醒，本地合并通知避免惊群；排队超时自动踢出，全程 SSE 推送排队状态。

11.2 8 线程池 + TTL 透传

按工作负载特征配置 8 个独立线程池（MCP 批量调用、RAG 上下文组装、多路检索、内部检索、意图分类、记忆摘要、模型流式输出、对话入口），队列类型和拒绝策略各不相同。所有线程池用 TtlExecutors 包装，确保用户上下文和 Trace 信息在异步线程中不丢失。

11.3 全链路 Trace（AOP）

@RagTraceNode + @RagTraceAspect：每个环节的耗时、输入输出、异常信息都有记录，落 t_rag_trace_run / t_rag_trace_node，可视化排查。

11.4 会话记忆压缩

滑动窗口 + 自动摘要压缩 + TTL 过期，避免长对话 OOM / Token 爆炸。

11.5 认证鉴权

基于 Sa-Token 的用户认证体系，不是裸奔的 API；UserRole 区分普通 / 管理员。

11.6 其他生产特性

特性说明
限流全局并发限制 + 用户级限流，防模型调用被打爆
熔断模型健康检查 + 失败计数，自动熔断不可用模型
流式输出SSE 实时推送，首包探测保证模型切换用户无感知
可观测性基于 AOP 的全链路 Trace
